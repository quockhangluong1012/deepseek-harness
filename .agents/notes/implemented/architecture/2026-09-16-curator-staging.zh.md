# Agent Note：整理器在移动任何东西之前先分选失败的技能

Status: implemented

[English](2026-09-16-curator-staging.md) | 中文

## Problem

Review-v6 §4.3 要求在整理器已有的通过里加入一个"浅睡眠"分选步骤：扫描遥测，把值得注意的东西写进台账，不碰其它任何东西。Batch 3 刚刚给遥测存储加上了该步骤所需的结果信号——`failureCount` 与 `lastOutcome`——过滤器这才终于有真实数据可读。

两个事实决定了这次工作的形态。该通过已经有一套关于置顶、受保护名称以及随包附带或 hub 来源的排除策略，因此分选必须决定沿用其中哪些。而 `/curator ledger` **只列出通过**，所以一个没有读取面的分选台账，在写下第一行的那一刻就成了死重。

## Decision

**选择是纯函数，策略留在通过里。**`src/stage.ts` 放着 `stageCandidate`——当 `useCount + failureCount >= stageMinUses`（默认 20）且 `failureCount / (useCount + failureCount) > stageFailureRate`（默认 0.3）时记录被分选，这正是 Batch 3 写在字段上的比率公式。样本量门控这个比率，因为三次加载的完美比率说明不了什么；比较是严格的，因为恰好等于阈值的比率尚未超过它。`orderStaged` 按最差在前排序，以名称作平手裁决，并写成泛型，让台账读取保留其额外的 `at` 字段而不必强转。

**分选沿用该通过的排除集，唯独不减置顶。**随包附带与 hub 来源以及 `protectedNames` 永不参与分选——它们本就完全在整理范围之外。而置顶技能**会**被分选：置顶保护的是技能不被移动，而不是不被查看，而分选不移动任何东西。这意味着要调整通过循环的顺序，让置顶检查发生在分选之后；跳过计数仍然每个技能只计一次。

**是证据，不是移动。**被分选的技能追加一条 `stage` 台账条目——名称、两个计数、比率与理由——其它什么都不变。`backup.enabled` 管住这次写入，而那正是该开关已经记录的语义（"快照与台账写入的总开关"）。计数就是去重键，因此在台账上已有计数的技能不会被重复追加；没有这一步，每次通过都会为每个失败技能加一行，永无止境。

**读取面，因为台账此前没有。**`staged()` 读取每个技能的最新条目，最差在前，`/curator staged` 列出它们；`/curator status` 增加计数与最差比率，`/curator run` 列出本次通过分选了哪些。现有的台账命令都只列通过，因此一种没人能读的新条目类型会变成只写记录。

## Alternatives considered

**把归并候选集扩大到每个被分选的技能。**已拒绝。归并刻意只覆盖 agent 创建的技能——它会补丁与归档软件包，而用户主导的技能不是整理器可以重写的。分选是操作者证据与 §4.3 要求的有效性指标；它读取的失败已经通过调查的 `failures` 字段到达归并裁决。

**为浅睡眠阶段再加一个定时器。**已拒绝：§4.3 说要复用已有的通过，而本包自己的规则是宿主级只用一个定时器。分选搭同一次 `run`——`maybeRun` 也因此免费获得它，包括闲置门控。

**用独立存储代替台账。**已拒绝：台账已经承载执行者、时刻与证据，是只追加的，而且正是回滚与 `/curator ledger` 读取的东西。第二个存储需要自己的一套保留与一致性说法，而这份数据从不被修改。

**把分选放进 `surveyCandidates`。**已拒绝：按契约该方法是供归并 fork 使用的读取，永不写入。分选要写一条台账行，因此属于该通过。

## Consequences

如今每一次通过都会留下操作者证据：遥测跨过两道门的技能——至少 20 次记录到的结果，且失败占比严格高于 0.3——会获得一条 `stage` 台账条目，记下名称、两个计数、比率与理由。`/curator staged` 列出的正是这些条目，`/curator status` 统计它们的数量并附上最差比率，`/curator run` 则列出本次通过分选了哪些。没有任何东西被移动：分选只是把技能标给复核，因此没有软件包、文件或置顶会发生状态变化。

置顶仍然会被分选。置顶技能产生的证据与其它技能完全一样，因为置顶保护的是它不被移动，而不是不被查看；通过循环的检查顺序为做到这一点而调整，而跳过计数仍然每个技能只计一次。

代价是：每个新近失败的技能多一条台账行——其上限由计数去重划定，因为仍在失败但计数已记在台账上的技能不会被重复追加——而且这次写入处在 `backup.enabled` 之后，因此关掉该开关的部署完全收集不到分选证据。`stage` 还是台账里第一种现有「只列通过」的清单无法展示的条目，这正是 `staged()` 与两个状态面存在的原因。

## Testing

阈值处、样本门控之下、以及从未加载过的技能等边界情况；跨多次通过与跨计数变化的去重；只预览不写入的 dry-run；`backup.enabled: false` 不写任何东西；置顶被分选而受保护被跳过；按比率排序与按名称平手排序，后者用两种输入顺序的二元素数组，从而无论排序实现如何都能跑遍比较器的两个分支。两个包在本次改动触及的行上，语句、分支、函数与行覆盖率均为 100%。

## Deferred

回合级技能结果（技能的建议是否奏效，而非加载是否返回），那是 GEPA 触发器需要的信号；分选到批准的转化计数，§4.4 的指标想要它，而它需要台账尚不携带的 `adopt`/裁决关联；以及 GEPA 触发器与优化器（Batch 5-6）。
