# Agent Note: 会话检索新增向量通道与排名融合

Status: implemented

[English](2026-09-13-session-search-vector-channel.md) | 中文

## 问题

会话检索只做文本匹配。调用方只能找到包含它所输入的那些词的会话；用与转录不同的措辞提问便会一无所获——这正是嵌入能力本要弥合的缺口。

填补它引出三个规范未回答的问题。第二份排名放在哪里：全文后端内部，还是其旁？当部署没有挂载任何嵌入提供方时，服务返回什么？两份排名不一致时，融合又该做什么？

另有两项约束来自既有引擎而非规范。`_replacePersistedSession` 与 `_replaceLiveSession` 是同步的，并运行在串行化的 reconcile 事务内，因此若在索引文档时写入向量，就会让该事务在跨网络调用期间一直打开。而候选查询完全围绕 FTS5 的 `MATCH` 与 `highlight()` 构建，语义检索根本用不了它们。

## 决策

`SessionQueryEngine` 新增两个成员。`searchSessionsSemantic` 是抽象的，因此每个提供方都必须作答。`searchSessionsHybrid` 在定义中是具体的：它调用两个通道，并以标准常数 60 的倒数排名融合二者——两个通道都排得靠前的会话，胜过任一通道单独找到的会话，这正是同时运行二者的理由。融合放在定义里，使融合规则只写一次，而非每个后端各写一份。

通道本身位于 `dsh-session-query-sqlite`，与词法通道并列，共享其过滤器与命中装配。新增的 `SEMANTIC_CANDIDATES_SQL` 在不使用 `MATCH` 的情况下选出经过过滤的语料，并投影出同样的列外加每个文档的 rowid，因此命中由既有代码装配，语义命中只是携带纯文本摘录，而词法命中携带高亮摘录。

向量以内容哈希与模型为键，而非 rowid。因此被重新索引的文档绝不会被喂给先前占据其 rowid 的那个文档的向量——而那正是显而易见的设计会交付的故障。存储放在 `persisted_vectors` 表中，schema 版本随之提升到 9，使既有的派生索引就地重置。

嵌入发生在串行化区段之外：通道在其中读取候选，在之外嵌入并排序，再把刚产出的向量在一个简短的串行化步骤中写回。没有挂载嵌入服务的部署会以 `SESSION_QUERY_SEMANTIC_UNAVAILABLE` 拒绝该调用，而不是悄悄用调用方并未要求的词法结果作答。

## 考虑的替代方案

**在后端内部融合。** 可以让提供方自己负责融合。这样每个后端都能调自己的权重，代价是每个后端各存一份规则；改由定义负责之后，所有提供方以相同方式融合，调用方在任何地方都能依赖同一种合并顺序。

**在索引期间嵌入。** 在 `_replacePersistedSession` 中写向量能让存储始终最新。但它也会让 reconcile 事务在提供方调用期间一直打开，那是该引擎的加锁设计承受不了的。按 `maxVectorCandidates` 有界地惰性嵌入，保住了写入路径的同步性，并且只在有人索要向量时才付出代价。

**按文档 rowid 存向量。** 这是最显然的键，也是错的：会话变化时文档会被整体删除并重新插入，因此 rowid 会比它命名的那个文档活得更久。以内容哈希为键，让过期命中成为不可能，而不只是不太可能。

**没有提供方时回退到词法检索。** 静默降级会让调用方以为自己拿到的是语义结果。拒绝则点明了缺失的能力。

**返回两份未融合的排名。** 调用方本可自行融合。但每个调用方都要实现同一套算术，而且彼此的排序还会各不相同。

## 后果

现在可以按并未出现过的措辞找到会话，而且两个通道都认可的会话会排在只有一个通道命中的会话之上。`searchSessions` 与 `searchEvents` 未变，因此此前存在的行为没有任何改变。

代价付在一个语料上的首次语义检索：通道会嵌入它尚未持有的文档，上界为 `maxVectorCandidates`（默认 2000）。此后对持久文档的检索只嵌入查询。活动文档不入库，因此每次检索都会嵌入它们，并由嵌入服务自身的缓存吸收。

抽象服务的每一个实现者都必须回答新方法：一个生产后端，以及仓库内的十一个测试替身、夹具与基准。测试替身选择拒绝，用以模拟没有向量通道的部署。

向量存储不做清理：离开索引的文档会把它的向量留在原处。该表以内容哈希为键，且只经精确查找读取，因此残留行是死重，而不是错误答案；这一点记录在此，而不是默默接受。
