# Agent Note：进化预算策略与突变指令

Status: implemented

[English](2026-09-22-evolution-budget-and-mutation-instructions.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` 描述了一个为自身搜索定价、并修订自身变异策略的进化引擎，而仓库此前只建成了两者的浅层一半。

- §37 的预算控制器列出五个维度——`max_rollouts`、`max_tokens`、`max_cost`、`time_limit`、`parallelism`——而 `evolution-budget` 只为其中两个定价。批次无法携带成本上限、截止期或并发上限，结算也无从对它们发声。
- §37 的分配策略——高潜力候选获得更多预算、低潜力候选提早停止、新奇候选获得探索预算——只是按调用者指定的类别索引的四个固定乘数。没有任何东西读取候选的记录证据，因此类别是断言而非判定。
- §38 的逐轮减半是一段没有调用者的纯算式 `halvingRounds`。没有任何存储持有筛选过程所起始的候选池，因此调度无从由任何东西推导。
- §27 列出七个资源感知目标。它们中没有任何一个在任何地方有读数，其中两个——内存占用与上下文用量——更是完全没有记录来源。
- §9 的变异策略演化要求突变所发送的指令成为可记录、可修订之物。`evolution-operators` 依据结果为算子排序，而指令本身则是硬编码在被停用优化器的算子目录里的字符串。

## 决策

1. **§37 的维度加入了那些冻结函数已经在构建的记录。** `maxCost`、`timeLimitMs` 与 `parallelism` 是分配上的可选字段，`cost`、`parallelism` 与 `backgroundTokens` 是支出上的可选字段，由新的纯函数 `dimensionCeilings` 定价。`buildAllocation`、`withinAllocation`、`settle` 与 `multiplierFor` 保持进化执行器所调用的签名，按冻结的四个函数编写的调用者构建出的分配与从前一致。
2. **只有当两侧都被记录时，一个边量才被测量。** 当分配没有为某上限定价、或某次支出缺少该测量时，成本、截止期与并发全程报告 null，因为部分加总会读作整批的数字，而只覆盖部分批次的峰值可能低于该批实际越过的上限。`withinAllocation` 现在读取结算，因此一个此前看不到的、已定价且已记录的维度可以使其判为越界。
3. **分配策略是作用于记录在案的池的一条纯规则。** `policyFor` 按配置的阈值读取候选已记录的运行次数、通过与新奇度，返回类别、§37 分支与数字；批次记录它所筛选的池，`allocateForCandidate` 则通过该规则为池中某个候选定价，因此由策略定价的类别始终可追溯到记录证据，且记录在案的原因会点名产生它的分支。
4. **`halvingRounds` 得到了它的调用者与它的池。** `screeningSchedule` 由该批次记录在案的池推导各轮，点名每轮评估并保留多少、最后一轮留下多少。某一轮实际保留哪个候选仍是被停用优化器的决定；本存储推导筛选的形状，而非它的判定。
5. **§27 的目标是读取而来的，从不估算。** `objectiveReadings` 从记录在案的池推导质量与可靠性，从记录在案的支出推导延迟、成本与后台算力，并把内存占用与上下文用量报告为 null 且点名所缺失的记录。
6. **突变指令成为记录，并带来一个受限的微调。** `evolution-operators` 为每个算子与产物类持有一条候选指令，连同提案的原因、判定计数与最近一次判定的原因。排序在结果得分之上叠加 `instructionWeight × (接受 − 拒绝) / 判定数`，因此端住的提案抬升其算子、失败的则压低它，幅度受配置权重限制。
7. **README 配对陈述 §26 地图。** 两个包都点名自己覆盖哪一级的记录那一半——算子为第 3 级，预算为第 5 级——并说明在 Web profile 以 `disabled: true` 挂载优化器期间哪些仍不可达。

## 考虑过的替代方案

- **为新维度使用带 zod 默认值的必填字段。** 已否决：默认值会物化出一个没有任何东西记录过的上限与测量，`withinAllocation` 随后会拿旧记录从未携带过的数字去判定它。缺失不等于零，而行模式用 `.optional()` 明确表达了这一点。
- **从记录的分数推导存活者。** 已否决：轮次之间的筛选器属于被停用的优化器，因此存活判定属于运行该筛选器的消费者。本存储推导每轮评估并保留多少候选，到此为止。
- **在 `candidateClass` 旁另存一个 `branch` 字段。** 已否决，因为那是一个事实的两个名字：四个类别就是四个分支。分支句子随记录在案的原因一同保存，那也正是读取者渲染的内容。
- **为候选池新建一个域。** 已否决：该池是同一批次的预算证据，属于 `evolution_budget` 的第三张表，调度在那里读取它而无需跨存储连接。
- **在预算存储内部实现一个指标层。** 已否决：`evolution-metrics` 拥有指标面，第二套成本读数将不得不与其算力开销比保持同步。预算存储暴露读数；指标层仍是唯一的报告。
- **为池调度新建一个纯模块。** 已否决：`halvingRounds` 已经拥有那段算式，第二个筛选模块只会成为它的包装。
- **依据判定改写优化器的指令目录。** 已否决：存储记录并推荐，优化器保留它自己发布的字符串，施加提案是部署的决定——与进化组其余部分所持的记录而非强制边界一致。
- **用指令得分取代结果得分。** 已否决：指令判定是判定间的代理读数，因此它们在结果证据之上做受限微调，而不会推翻一个已被证明的领先者。

## 后果

- `evolution-budget` 在既有接口旁新增 `recordPool`、`allocateForCandidate`、`pool`、`schedule` 与 `objectives`，三个新的纯导出（`dimensionCeilings`、`screeningSchedule`、`policyFor`）加两个读取助手（`recordedTotal`、`objectiveReadings`），六个用于新上限与策略阈值的配置字段，以及第三张域表。
- `evolution-operators` 新增 `recordInstruction`、`judgeInstruction`、`instruction`、`instructions` 与 `recommendedInstruction`，一张 `instructions` 域表，以及一个 `instructionWeight` 配置字段。`rankOperators` 接受一个可选的第四个参数，因此所有既有调用者照常工作。
- 两个域各新增一张表且版本仍为 1，因为没有任何已提交行的形状发生变化：在本工作之前写下的记录会在新字段缺失的情况下打开，其未测量的维度报告为 null。
- Main 为 §32 新算子档位接线的 `evolution-actuator` 循环读取 `recommendedInstruction(artifactClass)` 并报告它拿到的行。
- 两个包在其 `src` 树上都带有逐文件 100% 覆盖率门槛，其 README 配对各自陈述所覆盖的元演化层级。
- **已定价的截止期会随日历时间关闭闸门**，因为截止期衡量的是从分配到最近一次记录支出的跨度，而不是已完成的工作。一个超过其 24 小时默认值仍留开的批次会读作已花尽，而执行器的预算循环——它依 `withinBudget` 设闸并把规则委托给本包——会让该类别的工作停下，直到有更新的分配为其定价。这是 §37 的时间上限在履行预算应有的含义，而非意外；回合节奏更慢的部署应调高 `baseTimeLimitMs`，README 也如此说明。

## 与计划的偏离

工单要求新维度为「带 zod 默认值的可选字段」；它们可选但不带默认值，原因见上面的替代方案。工单还要求 §27 的目标「与现有的质量/可靠性三元组并列」——即引擎的实测三元组（`pass`、`tokens`、`wallTimeMs`）——读数确实如此，其中质量与可靠性由记录在案的池推导，因为支出不携带通过。目标留在 `evolution-budget` 而未迁入指标层，是依父代理的指示，因此本批次不触碰其他任务拥有的任何包。

## 途中发现的修复

两个包已提交测试中有四处期望与其所运行的代码相矛盾，每一处都按其真实契约替换，而非重新钉住新措辞：

- `evolution-budget` 的累计结算测试期望的墙钟超支，用它自己的支出记录相对于同一测试上一行所断言的上限根本产生不出来；现在第二次支出同时越过两个上限，这正是该测试名称所描述的情形。
- `evolution-budget` 的预算内测试期望一笔 30000 token 的支出突破 40000 token 的上限；现在它检查累计支出实际具有的由内到外的转变。
- `evolution-operators` 的两个列表测试期望从按 `MUTATION_OPERATORS`（其中 `rewrite` 居首）排序的结果中得到 `['add-step', 'change-tool', 'rewrite']`；两者现在都期望规范顺序，其中一个还顺带覆盖了产物类平手规则。

## 测试

`node node_modules/vitest/vitest.mjs run packages/evolution/evolution-budget packages/evolution/evolution-operators` 通过 7 个文件、92 个测试；在 v8 覆盖率下，两个包的 `src` 树均报告语句、分支、函数与行 100%。

行为证据：分配携带已定价的成本、截止期与并发上限，支出对每一项结算出其边量，包括超支侧与未测量侧；`withinBudget` 在该批次越过的已定价维度上判为越界，并忽略没有任何记录的那个维度；对证据达到各自阈值的候选，策略分别返回增益预算、早停、探索预算与标准分支，批次把该分支记入分配的原因；筛选调度在由十个候选组成的记录池上点名每轮评估并保留多少、留下多少终选；目标从池与支出读出质量、可靠性、延迟、成本与后台算力，并把内存占用与上下文用量报告为 null 且点名所缺失的记录；候选指令连同其判定被记录，算子排序随受限微调而移动，被拒绝的提案沉到未试先验之下、被接受的则领先。

两个 README 配对都通过 `scripts/verify-translation-pairing.ts`。

## 未触碰的部分

此处没有任何东西阻断运行：超支的批次被报告，而读取 `withinBudget` 的调用者才是据以行动的一方（§58.12）；早停分支为更小的批次定价，而不是停下一次运行。截止期是唯一会随日历时间关闭闸门的维度，README 的限制一节对此明说而非留作隐含。轮次之间的筛选器仍属于优化器，因此不记录任何存活判定。没有任何存储改写优化器的指令，而执行器对推荐指令的使用属于父代理的接线而非本工作。乘数与策略阈值由配置给出而非习得，而 §26 第 5 级要改变它们，需要已结算的结果。
