# Agent Note: 失败反馈按会话记录，而非按回合推断

Status: implemented

[English](2026-09-13-evolution-feedback.md) | 中文

## 问题

学习回路此前没有任何关于"究竟哪里坏了"的持久证据。经验来自对话说了什么，技能遥测统计的是技能被加载与打补丁的次数，评分器只为已录制语料给出一个通过与否的数字——但没有任何东西记录某次工具调用失败了、它说了什么、以及同一故障是否反复出现。

这块空缺挡住了回路的反思那一半。GEPA 式的优化器需要的正是文本优化器所读取的那一对：一个度量得分，以及关于该次尝试为何不达标的自然语言反馈。Harness 已有得分与轨迹，反馈则无处存在。这也让失败本身不可读：一个跨四个会话发生四十次的故障，除会话日志外不留任何痕迹。

## 决策

`@deepseek-ai/dsh-evolution-feedback` 提供 `ctx.evolutionFeedback`，即按会话持久化失败工具结果的记录。

插件按投递原样观察 `session/event`。`tool/call` 按调用 id 记下；被标记为错误的 `tool/result` 会连同解析出的工具名与其可见文本一并记录，结果本身没有文本时回退到失败码。成功的结果不记录任何内容。待处理表在 `turn/end` 清空，因此在其回合结束之后才到达的结果记为空工具名，而不是留下过期的名字。

一条观测以"工具 + 消息"为键。重复出现会让 `count` 加一、把该条移到最前，并丢弃先前那条，因此一个撞上同一故障四十次的会话只留一条、计数为四十。消息在被用作键之前先做空白归一化并按 `maxMessageChars` 裁剪，单个会话最多按最新在前保留 `maxEntries` 条观测。

`summary(sessionIds, limit)` 按工具与消息合并所请求的会话。它累加每个失败的观测计数，保留最早的首次出现与最新的重复，并统计报告过它的不同会话数——因此"四个会话各出现一次"的故障排在"单个会话重复四次"之前，而这正是修复应该遵循的排序。条目先按计数、再按新旧排序。

此处不调用任何模型。失败结果自身的文本就是反馈；提取它零成本且是确定性的。

## 考虑的替代方案

**把失败观测并进评审器的回合缓冲。** 评审器已经看到同一条回合流、缓冲它并在 `turn/end` 冲刷，因此最省事的改法就是在它已有的缓冲里记录失败。它输在两点：评审器的单位是整个回合，且其提取是有门控的（冷却、文本下限、`enabled`），因此只要提取关闭，失败就会被悄悄丢掉——而那恰恰是部署最需要这些证据的时候；并且它的缓冲是为喂给一次模型调用而存在，并非供其他消费者读取。

**让模型把错误解析成散文反馈。** 反思维度的优化器读的是自然语言，因此失败本可由模型来总结。这是拿确定性的转录去换不确定且有账单的转录：工具结果里已经带着模型将要转述的文本，而转述会丢掉下一次修复必须匹配的那条确切消息。

**按作用域而非按会话作键。** 其余每个演进存储都以 `profile:workspaceId` 为键，因此反馈本可以沿用该形状并加入简报的作用域记录。它能免费换来跨会话合并，代价是要为每个事件解析作用域归属，并要回答"不在任何工作区内的会话，其反馈如何表现"。按会话作键让写入路径仅仅是事件的函数；调用方在读取时自行聚合它们关心的会话。

**把失败记录进技能遥测。** 遥测存储已经保存按技能的计数器，因此失败本可以变成又一个计数。遥测刻意统计的是使用——使用、查看、打补丁、生命周期状态——且其记录是按技能的，而非按次发生的。一个没有消息的失败计数无法告诉优化器该改什么。

## 后果

回路现在能被告知什么在反复失败，既确定又不花模型调用；并且答案按故障扩散的广度排序，而不是按单个会话重复的音量排序。

写这一版在发布之前就暴露了一个真实的并发缺陷。同一步骤的工具结果会一起到达，因此朴素的"先读后写"与自身竞争：同一 tick 内记录的两条结果各自读到记录不存在，各自写入一条新记录，后一次写入丢掉了先前的观测。本存储现在为每个会话给出一条写入链，使单条观测的先读后写决策绝不与另一条重叠，且每条链在作为队尾落定后即删除自己的映射项。两条规格——按会话的条数上界与跨会话聚合——在竞争实现下失败，在串行实现下通过。

权衡记录在包 README 中：只观测工具失败；域为每个会话保留一条永不清理的记录；观测不追溯，因此挂载之前就已失败的会话不可见；消息被裁剪意味着两条不同的长失败可能在同一条上相撞；空工具名是一种真实状态，而非错误。

在消费它的优化器趟次落地之前，`summary` 在仓库内尚无调用方。
