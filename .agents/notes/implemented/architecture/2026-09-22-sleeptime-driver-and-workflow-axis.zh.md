# Agent Note: 睡眠时驱动者与工作流轴线

Status: implemented

[English](2026-09-22-sleeptime-driver-and-workflow-axis.md) | 中文

## 问题

两个机制族都只落地了记录的那一半，没有任何东西据此行动。

§25 的睡眠时计算以带经济计划的存储落地，而所有写入者都只是测试。出厂产品中的 `/sleeptime` 报告空计划，因为除了单元测试没有任何东西预期过任务；[睡眠时注记](2026-09-22-sleep-time-compute.zh.md) 把心跳驱动的预期记为延后，包 README 的第一条 Known Limitations 也说空闲时间「是被计划的，还不是自动的」。经济学也没有端到端记录：`planFor` 算出净收益与理由，而 `precompute` 把理由丢在地上，因此缓存产物说不出是什么为它辩护。

§26 的元演化以五存储族落地，每次运行记录一份**标量**配置，而规范的阶梯有五层。第 2 层——「演化工作流」——完全没有表示：`EngineRun` 只持有四个不透明的组件选择，对它们运行的顺序一无所知，于是同样组件以不同顺序运行的两次运行被合成一份配置、通过率被混在一起，而 `recommend` 只能给出一个标量选择。README 也没有说明每个存储覆盖哪一层，以及五者都读为空是因为它们唯一的写入者 `evolution-optimizer` 以 `disabled: true` 出厂。

## 决策

**§25——在已记录复现之上的心跳遍历。** `evolution-sleeptime` 通过 `evolution-dreaming` 已在用的 `ctx.get('evolutionHeartbeat')` 接缝注册一个心跳任务 `sleeptime-anticipation`，由 `anticipateAll(signal?)` 运行一次遍历：

1. **预期由推导得出，从不捏造。** 遍历读取已挂载源已经记录下的发生——`evolutionRouter.outcomes()`，以及对每个被跟踪技能读取 `evolutionSkillTelemetry` 记录过会话的 `evolutionTrace.summary()` 行——由 `recurrenceOf` 统计 `recurrenceWindowHours` 内每个「源＋类别」。只有发生次数至少 `minRecurrences` 的类别才会被预期；`anticipationOf` 把其可能性设为它在复现发生中的占比、预期查询数设为它自身的复现次数、预期节省设为单次已记录发生的平均 token。`classKeyOf` 用源为类别加命名空间，因此读起来相似的技能与路由是两个候选。未挂载的源不贡献任何东西，没有任何复现的遍历则什么都不记录。
2. **预计算需要已记录的证据，而不是计划的一面之词。** 遍历只为同时出现在计划与已记录复现中的类别做预计算，因此操作者预期、计划给高分、但没有任何复现记录支持的任务会被跳过，而不是被填入编造的内容。
3. **决策随产物一起走。** `PrecomputeArtifact.decisionReason` 保存计划的理由，因此每份缓存产物都点明为它辩护的那次「离线成本对节省」比较，而 `precompute` 接受调用者给出的理由。
4. **命中来自已记录的轮次，经游标推进。** `hit(artifactId, occurrences)` 对产物自身类别中严格晚于 `servedThroughAt` 的每个发生记账，每次各记一次命中与那一轮记录在案的 token，并推进游标。在产物从未被服务时该游标是它自己的预计算时刻，因此在产物存在之前跑过的轮次永远不会被算作它的消费者，而在证据未变时重复遍历是空操作。这取代了由操作者提供 `hit(artifactId, savedTokens)` 的入口，那里的节省是调用者的猜测而非已记录的轮次。
5. **新字段构成一次域版本升级。** `evolution_sleeptime` 升到版本 2，`decisionReason` 与 `servedThroughAt` 默认为 null 且 `compatibleVersions: [1]`，因此已存的 v1 产物可打开，并从它自身的时刻起算。

**§26 第 2 层——工作流轴线。** `EngineRun` 现在携带 `workflow`，即一串已记录的 `WorkflowStep`——每个阶段点明它调用的 `EngineComponent` 与所用的选择，并处在运行执行它的那个位置上。`workflowIdOf` 将其渲染（`operators=portfolio-v1>evaluator=scorer-v1`），`configIdOf(config, workflow)` 用它收尾配置身份，因此相同组件以不同顺序运行是两个身份、两份摘要、两个候选。`recommend` 在配置之外一并返回工作流及其标识，其理由点名获胜运行执行过的序列。存储原样记录该序列：缺失时存为空序列，理由写明 `workflow unrecorded`，因为从配置反推顺序恰恰是第 2 层存在的意义所在。`evolution_meta` 升到版本 2，`workflow` 默认为 `[]` 且 `compatibleVersions: [1]`。

**§26——层级地图被写明。** `evolution-meta` 的 README 带一张表，逐层点名演化对象、覆盖它的存储与其状态；表里直说在 `evolution-optimizer` 以禁用状态出厂期间五层皆不可达、写入者被禁用不等于该层已实现，以及任何层级都不改变引擎运行的内容。

## 备选方案

- **从零预期，而不是从已记录复现推导。** 否决：规范要求「尤其在未来查询可预测时」做预计算，而已经挂载路由、技能遥测与轨迹存储的主机已经把那项预测以记录事实的形式握在手里。凭自己猜测去预期可能性的遍历会把离线预算花在自己的猜上，且无从审计。
- **把驱动者放进 `evolution-actuator`。** 否决：actuator 读取已记录的裁定并执行该裁定所许可的步骤，这正是它必须排在每个存储之后的原因。睡眠时预计算为尚未发生的未来产出产物，那是生产者，而不是对已记录之物的驱动；而且这次遍历需要存储自己的私有表，因此它属于该存储。
- **从配置推导工作流而不是记录它。** 否决：第 2 层的全部要点就是顺序是一个变量。推导出的序列会让同一配置的每次运行共享同一种工作流，于是任何一种工作流都不可能被推荐胜过另一种。
- **把工作流做成 `configId` 之外另一个分组键。** 否决：一个候选两个身份会诱使调用者按一个分组、按另一个排序。扩展 `configIdOf` 用一个键回答两个问题，且字段顺序由构造固定，因此身份永不依赖对象键顺序。
- **把工作流设为 `EngineRunInput` 的必填字段。** 否决：唯一写入者是优化器的记录接缝，而本次改动并不触碰它。必填字段要么让每一处已有的记录调用失败，要么迫使调用者断言一个它并未观察到的序列；可选字段诚实地记录缺失，而理由字符串会报告它。
- **为每个复现类别预计算所有产物类型。** 暂不采纳：遍历为每个类别缓存一份 `summary`，这是仅凭已记录复现就能填入而不必撰写散文的产物。其余类型仍是 `precompute` 调用，已记为限制。

## 后果

- 空闲时间现在是自动的：同时挂载心跳与三个源存储中任一个的主机无需操作者即可预期与预计算，而失败的遍历由心跳自身的 `lastError` 报告，不会中断同一节拍中的兄弟任务。
- 产物的回本账本现在有证据支撑。`hits` 与 `savedTokens` 计的是已记录轮次，`servedThroughAt` 为它们设界，`decisionReason` 说明产物为何被构建——因此 `savingsOf` 衡量的是相对离线支出的真实回报，而不是调用者的估计。
- 元存储的推荐会点名一种工作流。同样四个选择的两种顺序分别排名，`/meta recommend` 读回它所推荐的序列，理由字符串也携带它。
- 两个域升到版本 2 并带 `compatibleVersions: [1]`，因此已部署的存储可打开并保留其行。
- 层级地图现在是一段读者可以核对的话：五个存储已挂载、五条命令会作答、出厂 profile 中五层皆空、它们与证据之间只隔一个开关——优化器那一行。
- 两个 README 三元组与睡眠时注记都一并更新，注记中「心跳延后」的说法被就地改写，而不是留着与代码相互矛盾。

## 与计划的偏差

计划把 §25 的经济学规则与 §26 的工作流轴线放进同一改动，因为两者都是对「读取时推导一切」的存储所做的小幅补充。工作流轴线需要一件计划未预料到的事：`EngineRunInput.workflow` 必须保持可选，因为唯一的生产写入者是优化器的记录接缝，而本次改动并不拥有它。把缺失的序列记为空并在理由中说明，是这一层在其写入者被禁用时诚实的写法。

## 途中修复

- `evolution-meta` 的重启与摘要测试断言 `summaries()[0]` 是两轮配置的 `writer` 行。`summarize` 按任务类别升序分组，因此 `reader` 排在最前——该断言是错的，只因夹具当时另有一个缺陷才得以通过。它现在断言文档化的顺序（类别升序，再按得分），并通过查找定位 writer 行。
- 同一套件的 `runs()` 排序测试在冻钟片段之后紧接着记录两次运行，两次可能落在同一毫秒而落到运行标识平局规则上。现在用真实延时把二者隔开。
- `evolution-sleeptime` 的 `hit` 不能再接受调用者给的 token 数：只有已省 token 是某个已记录轮次实际花掉的 token 时，`savingsOf` 才有意义，而调用者对它未观察到的轮次无从知晓。

## 测试

`packages/evolution/evolution-sleeptime/tests/anticipate.spec.ts` 在无上下文的情况下覆盖纯推导：按源加命名空间的类别键、窗口计算及其对更早发生的排除、按类别分组与排序、复现门槛及其可能性占比与平局规则、产物摘要文本，以及受游标约束的消费——含从未被服务的产物、无消费者的情况与同一时刻的平局规则。`tests/driver.spec.ts` 启动心跳（禁用，以免启动计时器）、内存后端上的真实路由存储，以及轨迹投影的桩，然后驱动已注册任务：复现的类别按其已记录数字被预期，并按计划给出的理由预计算一次且带上该理由；第二次遍历既不新增任务也不新增产物；没有复现则什么都不记录；此后新记录的一次发生恰好记一次命中与其 token，再过两次遍历仍保持一次；计划给高分但背后没有已记录复现的任务保持未预计算，而 `plan()` 会报告它；技能复现来自遥测与轨迹行，而未加载过的技能与没有时刻的轨迹行不贡献任何东西；被中止的遍历读完了路由源并在技能之前停下；复现门槛、窗口、节拍与单次遍历上限都被尊重。`packages/evolution/evolution-meta/tests/store.spec.ts` 在原有内容上加入工作流：已记录序列经重启后仍在，未报告的序列记为空，而同样四个选择的两种顺序产生两个候选，其推荐点名该序列。两个包通过，且各自 `src/` 下每个文件的语句、分支、函数与行均达 100%。

## 顺带不动

优化器未被动过，因此出厂 profile 中没有任何东西填充工作流轴线，而层级地图把这一点写明。两个存储都不采纳自己的推荐：元存储仍然只推荐而不配置，睡眠时存储预计算出的产物也不要求任何一轮去查阅——想用上缓存摘要的模型必须主动索要，这正是本次改动未挪动的 §58.12 边界。记账把产物的 `taskId` 与加命名空间的类别键比对，因此标识为裸名、由操作者预计算的产物不会被自动记账；这一不对称被记为包限制，而不是用更宽松的匹配掩盖过去。
