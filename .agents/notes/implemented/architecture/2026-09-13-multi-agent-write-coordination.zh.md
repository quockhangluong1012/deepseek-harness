# Agent Note: 多智能体写入协调已由三套既有机制承担

Status: implemented

[English](2026-09-13-multi-agent-write-coordination.md) | 中文

## 问题

规范中的多智能体机制要求 harness 与其他智能体协调、避免冲突。两个智能体可能同时抵达同一份习得状态——同一进程内的两个会话，或共享同一 `$DSH_HOME` 的两个 harness 进程——并且各自都可能向同一作用域学习、给同一个技能打补丁，或在同一时刻推进同一技能的生命周期。

在新增协调层之前，必须先弄清现有机制已经阻止了哪些冲突，以及余下的边界究竟在哪里。

## 决策

不新增协调层。三套既有机制覆盖了单进程内的并发写入，而跨进程的边界归属于部署所选择的存储后端。

**域写入是串行的。** 每个写入原语都被排入其所在域的写入链（`dsh-storage-domain` 的 facility），因此针对同一条记录的两个写入者绝不会交错；而 `update` 在其自身任务的链槽位上判定记录是否存在，而不是在调用时判定。JSON 后端正依赖于此：`storage-json/src/single-unit.ts` 明确写道它不在内部排队写入，因为"写入顺序属于调用方（域层的写入链）"。

**同作用域的工具调用是串行的。** `defineTool.parallelScopeKey(args)` 把不得重叠的调用分组：共享同一键的调用绝不重叠，而不同的键仍可打包进同一个并行池（`packages/core/tools/src/index.ts:1333-1336`）。会产生变更的工具会声明它，因此对同一文件或同一技能的两处并发编辑是被排序的，而不是彼此竞争。

**跨进程的原子性由后端决定。** `storage-json` 通过写临时文件、fsync、rename 来发布每一个变更文件——在 POSIX 与 Windows 上都是原子替换——因此读取方永远观察不到被撕裂的文件。其 README 用一句话同时给出了姿态与指引：它通过域层排序调用，适用于可检视的文件；需要高并发数据的部署应当选择 SQLite。`storage-sqlite` 默认使用 WAL，因此那种情况由 SQLite 自身的跨进程锁覆盖。

**每一次习得性写入都是可恢复的。** 演进写入有字节上界，按配置暂存、记录日志，并受整理器的快照、台账与回滚覆盖。因此在竞争中落败的写入，是某条记录上的一次更新丢失，而不是学习回路被悄悄损坏。

## 考虑的替代方案

**在 `$DSH_HOME` 上加一个锁文件。** 进程级锁能一次性让所有域的跨进程写入变得安全。但它同时会为所有域——会话、设置、凭据——改变写入契约，只为解决一个仅由演进家族提出的问题；而从特性包去绕过拥有发布权的存储后端，本身就是错的层次。后端自己给出的、有据可查的答案是：并发重要时选择 SQLite。

**为每个演进作用域增加一个持久租约。** 租约能让一个智能体在它学习期间独占某作用域，这更接近规范所描述的东西。它引入了一个新的持久面，并带来自己的崩溃恢复问题——持锁者死亡必须可被察觉、其租约必须可被打破——而 harness 并不存在能安全裁决此事的第二个观察者。对一个 P2 机制而言，代价远高于价值。

**把所有习得性写入都路由给一个中枢智能体。** 单一属主智能体能彻底消除并发写入者。但它也会让学习依赖于该智能体存活且可达，而这与家族赖以成立的本会话语设计恰恰相反：每个作用域都从自己的回合中学习，就发生在已经持有这些回合的进程里。

## 后果

多智能体要求在实践中最常出现的情形下——同一 harness 进程内的并发写入者——已经满足；而余下的情形是一项有据可查的部署选择，而非未经审视的空白。希望获得更强跨进程保证的维护者，现在有了一个明确答案（SQLite 后端），而不必去设计一个新子系统。

代价是这一保证并不统一：在 JSON 后端上让多个 harness 进程共用一个 home 的部署，可能会在某条记录上丢失一次更新，由最后写入者胜出。这一点记录在部署选择后端的地方，而不是演进包内部，因为拥有发布权的正是那一层。
