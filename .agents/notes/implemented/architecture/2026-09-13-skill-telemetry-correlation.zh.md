# Agent Note: 技能遥测把加载与会话关联起来，使整理得以反思真实失败

Status: implemented

[English](2026-09-13-skill-telemetry-correlation.md) | 中文

## 问题

整理能看见一个技能被用了多少次，却永远看不见用时发生了什么。技能遥测以技能名为键，统计加载、查看与变更；失败反馈以会话为键，记录坏在哪里。二者之间没有任何连接键，因此"该技能在发挥作用期间观察到的失败"无法推导——而合并 fork 作为 harness 中唯一具备反思能力的趟次，只能凭技能自身的文本与计数器来决定它的去留。

这使得反思型优化器的"反思"那一半无物可思。`patch` 裁决只能复述技能作者的意图，无法回答究竟坏在哪里。

## 决策

`SkillUsageRecord` 新增 `sessionIds`：加载过该技能的会话，最新在前、去重，以存储的 `maxSessionIds`（默认 `20`）为上界。由 `markUsed(name, source, sessionId)` 写入，被动 `tools/post-execute` 观察器提供 `exec.agent?.session.id`——因此关联随加载一并到达，消费者无需额外接线。查看与变更不记录会话。

`SurveyCandidate` 新增 `failures`：关联会话中记录的每个失败的工具、消息、观测次数与报告的会话数，出现最多者在前，以整理器的 `maxCandidateFailures`（默认 `5`）为上界。`surveyCandidates` 从 `ctx.get('evolutionFeedback')` 收集它们——该接缝保持可选，未挂载时给出空列表而非失败。

这些失败随合并 fork 本就会收到的调查 JSON 一起送达，因此既有趟次在打补丁之前会先反思真实观测到的失败，而每一次写入仍然经由整理器的快照、台账与回滚机制落地。没有新包，也没有第二条技能写入路径。

## 考虑的替代方案

**在读取时从会话日志做连接。** 关联本可以在每趟中按候选去其会话里搜索 `skill` 工具调用来推导。那要为每个候选、每趟付出一遍历史扫描，并依赖排名检索接缝已挂载且返回正确的行；在加载点直接写下会话是 O(1)，且不依赖任何东西。

**另建一个优化器包。** 一个 GEPA 形状的趟次本可以自成一体直接消费反馈。但"反思并变更"这一半已经以合并 fork 的形式存在——有界工具循环、白名单、成本台账、整包规则——而第二个包将需要自己的技能写入路径，以及自己的快照、台账与回滚，从而复制整理器已经发布、且已经针对测试过的安全工具集。

**把失败反馈改按作用域作键。** 把失败存到作用域标识之下本可彻底消除这个连接，因为两侧会共用同一个键。它在反馈存储建成时就已因另一原因被否——按事件解析作用域归属需要工作区成员关系——此处也同样被否：为了连接而付出的代价，是在每条加载时本就要写的记录上多一个字段。

**连查看与变更也一并关联。** 人工查看与 `skill_manage` 补丁本也可以记下各自的会话。查看并不构成"技能失败"的证据，而列表是有界的，噪声会把真正携带信号的加载挤掉。

## 后果

反思趟次现在能被告知真正坏在哪里，而这个连接键也为日后的任何优化器准备就绪。

权衡记录在两个包的 README 中：关联仅限最近 `maxSessionIds` 个会话，且仅限加载；在本变更发布之前加载过某技能的会话不带关联；调查框会随其携带的证据一同增长，因此候选仍会在 `maxInputBytes` 压力下从尾部被丢弃。`maxCandidateFailures` 的默认值因此定得较低——证据与候选本身共享调查框的字节预算。
