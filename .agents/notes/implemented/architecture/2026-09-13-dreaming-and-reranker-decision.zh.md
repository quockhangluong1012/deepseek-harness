# Agent Note: Dreaming 固化已记录的失败；混合检索不带 reranker 交付

Status: implemented

[English](2026-09-13-dreaming-and-reranker-decision.md) | 中文

## 问题

规范中有两项机制尚未实现，它们引出的问题各不相同。

**Dreaming 固化**（§5）通过一个三阶段周期与六信号加权综合分，把反复出现的观察固化为持久记忆。规范用 cron 定时任务扫描每日笔记来驱动它，而这两者在本仓库都不存在：本仓库通过 heartbeat 调度空闲触发的工作，也不保存每日笔记。规范还指定两份文档——叙事写入 `DREAMS.md`，幸存者写入 `MEMORY.md`——而本仓库只有一份由模型拥有、且已由评审器写入的经验文档。

**Reranker**（§15.3）是对 `(query, document)` 对的交叉编码器。本仓库没有交叉编码器运行时、没有 Python、也没有 ONNX：诚实的选项只有引入一个、每次检索调用一次模型，或者不交付它。

## 决策

**Dreaming 以 `dsh-evolution-dreaming` 交付**，把规范的三个阶段对着本仓库真正拥有的东西来读。

候选来自该作用域已记录的失败，读取自 `dsh-evolution-feedback`。这一选择本身就带来了综合分所需的全部信号：一条失败已经记录了它被观察到多少次（`frequency`）、出现在多少个会话中（`query diversity`），以及介于哪两个时刻之间（`recency`、`integration`）。为了喂给算法，不需要发明任何东西。

三个阶段保留其含义：light 汇集并去重，REM 推导主题并写下叙事，deep 是唯一写入持久记忆的阶段。提升进入插件自有的 `evolution_dreams` 域，而不是经验文档，因此模型与周期永远不会成为同一份文档的两个写入方。

权重是代码中的常量，因为它们就是算法本身；阈值、节奏与保留量则是经过校验的配置，因为它们随部署而异。每个信号在加权之前都经饱和映射归一化到 `0..1`，因此一条被观察到一万次的失败，也无法压过一条在每个会话中都出现的失败。自动周期向 `dsh-evolution-heartbeat` 注册，并对注册表已知的各工作区运行 `dreamAll()`。

**Reranker 不予实现。** 融合已经从两个通道产出单一排名，而每次检索增加一次模型调用，会用向量通道本要保护的延迟，去换一个融合排名本已具备的第二意见。该决定记录在此，而不是留作无声的缺失：规范中的 reranker 假定存在本仓库所没有的交叉编码器运行时，而引入它是比某条检索路径少一个阶段更大的决定。

## 考虑的替代方案

**把 dreaming 做成 `evolution-curator` 中的第三个阶段。** 评审器本来就在技能遥测上运行空闲周期。这样可以少一个包，但也会把两个不同的主题——技能生命周期与记忆固化——合并进一个插件、一份计划；而想调提升阈值的操作者，并不是在调技能归档的那位。

**基于每日笔记目录做 dreaming。** 这是规范的字面读法。本仓库没有这样的目录，于是该周期将不得不创建并维护一个唯一的消费者就是它自己的目录。

**把提升写入由模型拥有的经验文档。** 这能让被提升的陈述立刻对模型可见。它也会让该文档拥有两个写入方，而评审器对它的压缩会悄悄丢弃周期刚刚提升的内容。

**把交叉编码器 reranker 做成新的能力接缝。** 那是对 §15.3 最忠实的读法。但在仓库内没有提供方的情况下，它将是一个无人实现的 Definition，而能力接缝规则禁止这样做。

**经 `ctx.llm` 用 LLM 做 reranker。** 它契合插件架构，也会在每次检索上花掉一次模型调用——包括那些正是为了变便宜才引入内容哈希缓存的检索——并且它会给融合排名已经排好序的对子打分。

## 后果

一个反复以同样方式失败的作用域，现在可以让那条失败被提升为持久记忆，而无需人工逐条批准；衰减规则则防止这份记忆无界增长。

各项权衡记录在包 README 中：在接入嵌入提供方之前相关性基于词面；提升尚未被注入模型上下文；heartbeat 节奏按部署取单一值；以及 `/dream` 命令可为当前作用域运行整个周期或单个阶段。

该服务渲染在子系统页与 capability-seams 图上，且 `dsh-command-evolution` 现已导入它——这正是投影能到达该包的原因。

检索保持其双通道融合，不增加 rerank 阶段。需要 rerank 的部署日后可以加入提供方，而不改变调用方已依赖的融合排序。
