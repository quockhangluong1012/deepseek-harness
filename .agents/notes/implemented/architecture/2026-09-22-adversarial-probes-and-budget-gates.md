# Agent Note: Adversarial probe generation and the §37 budget gate

Status: implemented

English | [中文](2026-09-22-adversarial-probes-and-budget-gates.zh.md)

## Problem

`specs/evolutionary-harness-v11-deep-research.md` §45 asks for "a dedicated adversary" with the loop `Generator → Candidate → Adversary → Find weaknesses → Repair → Verify`, targeting eight weakness families; §14 lists "Adversarial Example Generator" among the mechanisms that make the benchmark itself evolve; §32 says a stagnant skill "automatically switch[es] strategy"; §37 gives every experiment a budget. The recording halves all existed, and three of them had no consumer:

- `evolution-adversary` stored probes, the eight-family vocabulary, the next-category challenge, and the §46 defense checklist. Every probe came from an operator typing `/adversary probe <skill> <category> <probe>`, so a weakness the *engine* had already recorded — a §43 uncertainty signal, a curator regression debt — never became a probe. The store's own README stated it: "Executing probes against a skill and judging weakness remains an operator's job."
- The benchmark store's `admit` path was wired to three recorded sources (feedback failures, curator debt, curriculum proposals) and no probe ever reached it, so an adversarial probe stayed a line in a probe log instead of entering the evaluation set.
- `recoveryStep` reported §32's `newOperators`, `newEvaluators`, and `newModel` rungs `unactionable` because no store records such a switch. That report was honest but named no store, so a reader could not tell an architectural gap from an omission.
- `evolution-budget` priced a batch by candidate class and settled spends, and its `withinAllocation` rule was consulted only inside the optimizer's own `run()`. The actuator's loops — the only runners the shipped profile enables — consumed wall time with no allocation read, so a spent batch could stop the optimizer and nothing else. §38's "low-potential candidates → early stop" therefore had no enforcement point outside the disabled package.

## Decision

Seven narrow decisions, all inside `packages/evolution/evolution-actuator`.

1. **One new loop, `adversary`, generated from recorded evidence.** It reads the §43 uncertainty signals and the curator's open regression debt, generates one probe per recorded weakness, and records it through `evolution-adversary`'s existing `probe` path. `AUTOMATION_LOOPS` gains the loop, `LOOPS`/`LOOP_TASK_NAMES` gain `evolution-adversarial-probes`, and `Config`/`ResolvedConfig` gain `adversaryIntervalHours` (default 24) so its cadence is a deployment choice like every other.
2. **The weakness family comes from the store's closed vocabulary and the observation is verbatim.** A new `src/probe.ts` holds the two mappings: `signalProbe` maps each §43 kind to the §45 family it exercises — `disagreement → evaluator-gaming`, `low-confidence → ambiguous-instruction`, `instability → edge-case`, `retrieval-ambiguity → retrieval-trap`, `conflicting-evidence → contradictory-evidence` — and `debtProbe` maps an open regression debt to `tool-failure`, because that debt's merge key is a failing tool call. The probe text is `Probe <skill> for the recorded <family> weakness: '<observation>'.`: the family is the store's own word and the observation is the recorded text, so nothing here invents a weakness. The kind→family table is total, so every recorded kind reaches a family and an unrecorded weakness produces no probe rather than a defaulted one.
3. **A probe is recorded, never executed.** §45's second half — run the probe against a candidate and judge whether it exposed a weakness — needs an execution runner and a corpus the shipped profile has no store for. The pass records the challenge and leaves `foundWeakness: false` instead of reporting a run that never happened; a user comparing the probe store before and after a pass sees the challenge and not a fabricated verdict. That half stays operator-side.
4. **A generated probe is idempotent by content address.** Its `probeId` is the sha256 of the skill, the family, and the text (`adversarial-<32 hex>` — a shape no record key can break), and the pass skips a probe whose category and text the store already holds. The uncertainty signal stays recorded — this loop must not consume state the drain loop owns — so the provenance of the recorded challenge survives, while a repaired probe is never re-opened by the pass that keeps seeing it.
5. **§14's adversarial example enters the evaluation set through the existing path.** `probeTask` turns a probe into a `BenchmarkInput` whose capability is the probe's skill, whose task is the probe text, and whose gist is the observation the probe was built from; the pass admits it through `benchmark.admit` and the store's own content hash deduplicates it. Admission is gated on the capability being benchmark-shaped — the store already holds a task naming it — because an example with no evaluation set to join would be a benchmark task for a capability nobody evaluates. A first-time failure in a brand-new capability therefore produces a probe and no task until a curriculum proposal creates that capability's first task.
6. **§32's `newOperators` rung acts as a read, and the other two name the store they would need.** `recoveryStep` returns `operators` for that rung, and the recovery loop reports the instruction `evolution-operators`' `recommendedInstruction(skill)` returns for the stagnant skill's artifact class. It is deliberately a read: that store owns the operator portfolio and proposes the instruction to try next, the optimizer is the consumer of the same recommendation, and nothing in the shipped profile may rewrite the portfolio from the actuator — so the loop never calls `recordInstruction` or `judgeInstruction`. The rung is acted on exactly when a proposal exists; with the store unmounted, or holding no proposal for the class, the pass logs the rung `unactionable` naming which of the two it is. `newEvaluators` and `newModel` still return `unactionable`, and `recoveryStep`'s doc names each one: `evolution-evaluator-strategy` would have to take a proposed evaluator set, and `evolution-model-routes` a pinned role switch. A configured route is not a model switch, so it is not used to approximate one.
7. **Every loop's write is gated by the §37 allocation of its task class.** One helper, `underBudget`, sits between the rule that decides to act and the store call the rule names. It reads the allocations the budget store recorded for the skill or capability (new pure rule `governingAllocation` in `src/budget.ts`: newest `at`, then batch id, so the answer is total), and asks `evolution-budget`'s own `withinAllocation` over that batch's recorded spends. A spent class is left alone with a logged skip line — nothing happened, so nothing is written to a domain — and a class that ran settles against the same batch with the wall time it took, which is what lets a recorded ceiling stop the next pass of that class. An unmounted budget store, and a class no batch priced, run unmeasured exactly as before: an unpriced class has no ceiling rather than a zero one. Because enforcement is `withinAllocation` and not arithmetic re-derived here, the `max_cost`, `time_limit`, and `parallelism` fields `evolution-budget` adds in this batch are enforced without a signature change.

## Alternatives considered

- **Synthesizing the probe text in this package.** Rejected: the store's README already refuses invented weakness text ("execute probes ... remains an operator's job"), and a probe whose evidence is a sentence this package composed would be indistinguishable from a recorded one. The template carries a recorded observation and nothing else.
- **Defaulting an unrecorded weakness into `edge-case`.** Rejected: a defaulted family is a fabricated taxonomy entry, and a probe filed under the wrong family would corrupt `categoryCoverage` and every `challenge` the store derives from it. Nothing recorded means no probe.
- **Consuming the uncertainty signal after probing it, the way the drain loop does.** Rejected: the drain loop owns that signal's lifecycle, and a probe generator that resolved it would silently shrink the evaluation queue it does not own. Idempotence came from the probe's content address instead.
- **Executing the probe through the optimizer or the scorer to fill `foundWeakness`.** Rejected: that needs a runnable corpus and a candidate body, neither of which is in these stores, and it would add the model calls §45's execution half needs. The recorded half is what runs; the README names the missing half.
- **A new benchmark state for adversarial examples.** Rejected: `fresh` is where every admitted task starts, and §14's examples are ordinary hard cases that a candidate either passes or fails. A separate state would also need a rule for when it advances.
- **Reading the budget through `withinBudget(batchId)`.** Rejected: that method keys by batch, and a loop knows its task class (a skill or a capability), not which batch priced it. `governingAllocation` + `withinAllocation` applies the same rule with the key the loop actually has, and exposes no new store method.
- **Enforcing the ceiling inside each store.** Rejected: the loops are the runners, so the check belongs where the work starts; a store that refused writes over budget would also have no notion of which batch a caller's write belongs to, and would break the human `/benchmark admit` verb that shares it.
- **Throwing when a class is over budget.** Rejected: a spent batch is normal operation, not a defect. Throwing would land in the heartbeat's `lastError` and mark the whole pass failed — losing the other classes' work in the same pass — where a logged skip records the decision and lets the pass finish.
- **Approximating `newModel` with a `evolution-model-routes` pin.** Rejected per the mechanism's own wording: §32 asks to switch the model, and the route table chooses among routes a candidate may keep using. Reporting a route pin as a model switch would claim a change nobody made.

## Consequences

- `ctx.evolutionHeartbeat.state()` gains `evolution-adversarial-probes`, and `loops: [...]` accepts `adversary`.
- `recoveryStep` gains the `operators` step, and the recovery loop reads `evolution-operators` for the stagnant skill's artifact class. The rung is observable as a log line naming the operator and its instruction, or as an `unactionable` line naming the missing store or the missing proposal; the operator portfolio is never written.
- The package gains three workspace edges, `@deepseek-ai/dsh-evolution-adversary`, `@deepseek-ai/dsh-evolution-budget`, and `@deepseek-ai/dsh-evolution-operators` (`peerDependencies` + `devDependencies` + tsconfig references). No bundle row, root manifest, lockfile, or profile change: the rows and the lockfile belong to the integration pass.
- A pass of the new loop writes probes whose text carries the recorded observation, and admits the ones whose capability is benchmark-shaped. Both writes are deduplicated by the receiving store's own identity — the probe by content address, the task by content hash — so the loop's cadence cannot multiply either.
- Every loop's step now either runs under a recorded allocation or records a logged skip. The observable consequence of a spent batch is that the class's recorded work stops while every other class's continues.
- The probe store's `challenge` and `/adversary` output change meaning slightly: a category can now be covered by a generated probe that no operator typed, and reading `/adversary list` shows what the engine derived from its own recorded weaknesses.

## Deviations from the plan

- §32's `newOperators` rung was planned as unactionable-with-a-named-store and became actionable mid-batch, because `evolution-operators` landed the instruction API the rung needed. It acts as a logged read rather than a write: the rung stays honest about ownership, and the store's own ranking leader decides the instruction.
- The plan named "an actuator loop that GENERATES adversarial probes ... each grounded in an actual recorded failure **or contradicted claim**". A contradicted claim (`evolution-graph`'s `contradictionCount > 0`) is not used as a source: the graph's claims are per-scope, the actuator is host-wide, and the graph exposes no iteration over scopes to read them from — a source that cannot be read is not a source. `contradictory-evidence` probes are generated from §43's `conflicting-evidence` signals, which record the same disagreement at the point it was observed.
- Six of §45's eight families have a recorded source this loop can read; `prompt-injection` and `stale-memory` deliberately have none. `prompt-injection` is classified on the session ledger by the agent kernel (`FailureKind`) and reaches no evolution store — the feedback store aggregates failing tool results, so an injection that reached a tool is recorded as a `tool-failure`. `stale-memory` has writers (the memory store's sweep, the graph's retirement of superseded claims) but both are per-scope records with no host-wide read, the same blocker as the contradicted claim. Neither gap is closed by defaulting a probe into a neighbouring family, which is what the ticket's "the family comes from the recorded vocabulary" requirement rules out; both families stay operator-recorded.

## Testing

`node node_modules/vitest/vitest.mjs run packages/evolution/evolution-actuator` passes 42 tests. The new behaviour is pinned against real stores over an in-memory backend:

- one recorded `retrieval-ambiguity` signal produces exactly one probe of the `retrieval-trap` family and exactly one admitted benchmark task across two passes, and a probe the store already holds (with its repair flag) is left alone on the third;
- an open regression debt produces a `tool-failure` probe and its admitted example;
- a weakness in a capability the benchmark store never held records the probe and admits no task;
- a host with no uncertainty, curator, or benchmark store generates nothing, and one with no benchmark store still records the probe;
- a class whose batch is spent stops working — the signal stays queued, no task appears, and the skip line names the batch — while a class with room drains in the same pass and settles a spend against its own batch;
- a class no batch priced runs unmeasured;
- a stagnant skill on the `newOperators` rung logs the instruction `evolution-operators` recommends — and the portfolio it read stands unchanged — while the same rung logs `unactionable` naming the missing proposal, and naming the unmounted store, in the two cases the store cannot answer;
- every loop reports a successful pass with no store mounted.

Pure-rule tests cover the family mapping (all five §43 kinds), the verbatim evidence and stable content address, `probeTask`, and `governingAllocation` including the newest-wins, tie-on-instant, and empty cases. `src/` holds the per-file 100% gate: 8 files, 234 statements, 156 branches, 65 functions, 189 lines.

## Left alone

Probe execution and weakness judgment stay operator-side (§45's second half), and `/adversary probe` still records what an operator typed and `/adversary repair` still closes it. The optimizer keeps its own in-run budget check — this gate is on the loops, and the two are not merged. §46's defense checklist, including the `evaluator-gaming` family's operator-set rows for human spot checks, is untouched. `evolution-evaluator-strategy` and `evolution-model-routes` are read-only for this change, so those two §32 rungs still change nothing here; `evolution-operators` is read-only too — the loop reports its recommendation and never records or judges an instruction. The loops remain host-wide and sequential, and the budget gate inherits both limits: a class is the whole host's class, and one slow settle delays the classes after it in the same pass.
