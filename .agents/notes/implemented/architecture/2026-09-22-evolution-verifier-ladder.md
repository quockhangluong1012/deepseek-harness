# Agent Note: Verifier-first candidate admission

Status: implemented

English | [中文](2026-09-22-evolution-verifier-ladder.zh.md)

## Problem

`specs/evolutionary-harness-v11-deep-research.md` §12 names the design rule that separates AlphaEvolve's search from a model grading its own homework — "Do not use an LLM judge when a deterministic verifier exists" — and lays out the ladder that rule implies: level 0 schema validator, level 1 deterministic unit/invariant checks, level 2 domain simulator/tool execution, level 3 evaluator model, level 4 human review. §50 places VERIFIERS between the candidate generators and the evaluator ensemble. The repository had none of it as a mechanism:

- **Levels 0 to 2 existed inside a different question.** `evolution-scorer`'s `checkBehaviorContract`, `checkBehaviorRouting`, and `compareBehaviorReplay` judge a candidate: the contract gate is level 0's rule, the routing gate replays trigger queries through the real selector, and the replay gate compares a baseline revision against a candidate one. All three are in service of "is this revision better than its baseline" — they need a routing catalog, positive and negative queries, and a corpus to score both revisions against. The curator's admission question is different and much smaller: *may this body be committed?* Answering it with the scorer's path would spend fresh processes on a decision a frontmatter parse can make.
- **Level 3 existed nowhere.** No package offered a per-candidate evaluator judgment, and the audit's finding was the same one §46 makes about evaluator gaming: with no deterministic floor, there was nothing to prefer over a judge.
- **Level 4 existed only as an un-laddered gate.** `/skills approve` drops a staged entry *after* `skill_manage` already wrote the file — the README of `command-evolution` says so outright ("the skill file itself is written by skill_manage; approve only after that write landed") — so it decides a bookkeeping entry, not a commit.
- **The curator's patch gate validated one invariant.** `applyConsolidation`'s `patch` branch called `isValidSkillBody`, which checked parseable frontmatter naming the skill with a description. A body that passed was written whatever it said, and a body that failed was `skipped += 1` — a bare counter with no record of which check refused it or why.
- **The kernel's registry was unmounted.** `packages/runtime/agent-kernel/src/verification.ts` holds `CriterionVerifierRegistry`, a real tool-execution verifier registry, and no profile mounts it. Its request is a task contract with acceptance criteria, so it cannot answer a skill-body question without inventing criteria for it.

So the ladder's ordering rule — cheapest first, stop at the first decisive rung — was not implemented anywhere, and the one admission gate that did exist judged a strict subset of level 0.

## Decision

One new package, `packages/evolution/evolution-verifiers`, holds the ladder; the curator's patch branch is rerouted through it.

1. **The ladder is the package and nothing else is.** `runVerifierLadder(request)` walks `[0, 1, 2, 3, 4]`, records each rung's judgment, and returns the moment one refuses. The consult order *is* the cost order, so a body failing level 0 provably never reaches a simulator, a judge, or a human. `EvolutionVerifiers` (`ctx.evolutionVerifiers`) is a three-line service over the same pure function, so a host that wants one admission rule for several callers shares it without a second implementation.
2. **Levels 0 and 1 are the two rungs the package decides itself, and they decide from the candidate alone.** Level 0 is the frontmatter invariant `skill_manage edit` enforces, imported as `splitFrontmatter`/`validateSkillHead` from `dsh-evolution-skill-manage` — reused, never re-derived, so the ladder and the skill manager cannot disagree about what a committable body is. Level 1 adds the two invariants a body needs to be useful at all: a legal kebab-case skill name and non-empty instructions after the frontmatter. That is why the package's only host dependency is skill-manage, and why it opens no storage domain and calls no model.
3. **Levels 2 to 4 are seams, never stubs.** A `VerifierSeam` is a zero-argument function returning a `VerifierJudgment` (`passed`, `failed`, `abstained` with a reason). The caller composes the level-2 simulator, the level-3 evaluator model, and the level-4 human decision from whatever it has; the package knows only their order. An unmounted seam abstains with the reason naming what the host did not mount, and a mounted seam that cannot judge this candidate abstains itself — so the ladder never converts a missing judgment into a pass. A seam that throws propagates, because an unavailable simulator must fail the verification rather than be read as a quiet abstention.
4. **The verdict names the level that decided, or names the abstention.** `failed` carries `decidedBy` and that rung's reason; `abstained` carries `decidedBy: null` and a reason listing every abstaining rung; `passed` is reachable only when all five rungs passed. `rungs` carries every consulted rung in order, so a caller acting on an incomplete ladder can see exactly which judgment is missing.
5. **The curator's patch admission runs the ladder.** `applyConsolidation`'s `patch` branch calls `runVerifierLadder({ name, body })` and refuses on `failed`, pushing a `ConsolidationRefusal` — name, deciding level, the verdict's reason — into `ConsolidationApplied.refusals`, which `ConsolidationReport.refusals` carries out to the caller. A refused body is still counted in `skipped`. The curator mounts no level-2, -3, or -4 seam, so a body the deterministic rungs pass is committed exactly as before; what changed is that a refusal is now a named decision rather than an anonymous counter.
6. **`isValidSkillBody` is deleted.** Level 0 is that function with a reason attached, so keeping both would have left two frontmatter rules to keep in sync.

## Alternatives considered

- **Routing levels 0 to 2 through `evolution-scorer`'s behavior gates.** Rejected: those gates answer "is this revision better than its baseline" and require a routing catalog, trigger queries, and a scored corpus for both revisions. The curator holds a body and a directory. Importing the replay path to admit a patch would spend fresh processes where a parse decides, which is the exact inversion §12's rule forbids.
- **A second frontmatter validator inside the verifiers package.** Rejected: two rules for one invariant drift, and the skill manager's rule is the one `skill_manage edit` already enforces on every hand edit.
- **A `VerifierService` interface per level with its own context key.** Rejected as one-implementation indirection the caller would have to keep in sync with its own state: the caller already holds the judgment, so a function returning it is the smallest seam that can express the contract.
- **Mounting `CriterionVerifierRegistry` as a default level 2.** Rejected: its request is a task contract with acceptance criteria and its results are per-criterion command outcomes; a skill body has neither, so wiring it would mean inventing criteria to satisfy a signature. That registry's own gap — no profile mounts it — is a separate problem and is left alone.
- **Refusing a patch when the higher rungs abstain.** Rejected: the deterministic rungs are the whole available evidence in that path, and refusing every body the curator cannot simulate would end consolidation as a feature. The abstention is reported in the verdict; the commit rule for a deterministically valid body is unchanged.
- **Storing verdicts in a durable domain.** Rejected: nothing reads a verdict back by identity. The curator's report and its ledger rows already carry what was admitted and refused, and a domain with no reader is state without a consumer.
- **Gating `keep`, `consolidate`, and `archive` verdicts through the ladder too.** Rejected: those verdicts move or retain whole packages and name no replacement body, so there is no artifact for the rungs to judge. Their evidence is eligibility, pinning, and destination safety, which `applyConsolidation` already checks.
- **A `Config` field for the enabled rungs.** Rejected: a rung is enabled by mounting its seam, so a config field would be a second, weaker spelling of the same decision.

## Consequences

- `ctx.evolutionVerifiers` appears on the context and in the API catalog. The tsconfig alias, project reference, host/client registration, and the product profile row for the new package are wired by the coordinating change that lands this batch, not by the package itself, which declares `@deepseek-ai/cordis` and `@deepseek-ai/dsh-evolution-skill-manage` as its peers and imports nothing else.
- `ConsolidationApplied` and `ConsolidationReport` gain `refusals`; `skipped` keeps its meaning and still counts refused patches, so existing consumers are unaffected. The generated API catalog for `evolution-curator` changes with it.
- **One behavior tightens:** a patch body with valid frontmatter naming the skill but no instructions after the fence is now refused at level 1, where it previously committed. That is the intended stricter floor — such a body breaks what the skill routes on.
- The package registers nothing model-facing and reads nothing a model wrote, so no session event accompanies it and the model-visible ⟺ logged rule is untouched. A host that mounts a level-3 evaluator seam owns that request and whatever logs it needs.
- `evolution-curator` now peer-depends on `evolution-verifiers`, so a host that curates skills but omits the ladder package cannot mount the curator.

## Testing

`packages/evolution/evolution-verifiers/tests/ladder.spec.ts` drives each rung and the ordering directly: level 0 accepts the frontmatter invariant and refuses a body with no fence, a wrong name, a missing description, and unparseable YAML, each with its reason; level 1 accepts a legal name with instructions and refuses an illegal name, an empty instruction body, and a body with no fence; the ordering test mounts a passing simulator and asserts the level-0 refusal both names level 0 and never called the simulator, which is the spec's short-circuit as an assertion rather than a comment. The abstention tests cover the unmounted-seam case (three named abstentions, `decidedBy: null`), a mounted seam that abstains after a passing cheaper rung, an abstaining rung followed by a refusing one (the consultation stops there), the all-pass case credited to level 4, and a throwing seam that fails the verification instead of abstaining. `tests/verifiers.spec.ts` mounts the service over a real `Context` and checks the same two ends through `ctx.evolutionVerifiers`.

`packages/evolution/evolution-curator/tests/consolidate.spec.ts` pins the admission gate end to end: the direct `applyConsolidation` test now sends four patch bodies — no fence, wrong name, valid frontmatter with a blank instruction body, and a valid one — and asserts `refusals` equals level 0, level 0, level 1 with each reason, that only the valid body landed, and that its preimage and ledger row are unchanged; the fork-driven consolidation test asserts the same for the body the model proposed, so the level travels through the tool loop and the report.

## Left alone

The scorer's three behavior gates stay where they are: they answer a baseline-versus-candidate question the ladder does not ask, and `evaluateBehavior` remains the only path that approves a revision. `CriterionVerifierRegistry` remains unmounted — wiring it needs a task contract a skill body does not have, and inventing one here would have made the ladder's level 2 a different mechanism wearing the same name. Level 4 does not call `/skills approve`: that gate decides a staged entry after the file write, so the ladder takes a caller-supplied review judgment instead, and the approval path keeps its own semantics. The ladder judges one body at a time and stores nothing, so nothing here gates a skill's visibility to the model (§58.12 stays intact) and no host gets an admission history it did not keep itself.
