# Agent Note: 任务感知检索策略

Status: implemented

[English](2026-09-22-task-aware-retrieval-policy.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` §53 的 Hybrid Search 行要求一条"任务感知检索策略"，而 §39 列出了这样一条策略会变动的维度：检索来源、查询扩展、权重、重排器、MMR、记忆范围、图深度，以及活动记忆阈值。上一波建成了记录的一半：[`dsh-evolution-retrieval`](2026-09-22-retrieval-aware-evolution.zh.md) 记录每个会话所运行的配置，并按任务类别推荐越过证据闸门的最佳配置，而 `dsh-active-memory-context` 把在案配置作为旁路记录写下。它自己的 Agent Note 在同一句话里点出了缺口："没有任何东西自动采纳该推荐——注入器仍然完全按自己配置所写的内容运行。"

因此部署方可以不断积累逐任务类别的推荐，却从不运行其中任何一条。要补上这一半，还缺两件事：

- 注入器没有轮次任务类别的概念。从轮次文本里猜一个，恰恰是仓库要避免的"模型可见 ⟺ 已记录"违例：一个背后没有已记录证据的策略决定。
- 没有任何持久记录说明某一轮实际按什么检索。两个按不同配置检索的会话在归属表里可以区分，但一个会话若其各轮运行的是被推荐的配置，就无法区分。

## 决定

让 `dsh-active-memory-context` 按轮次的任务类别采纳该推荐，置于一个默认关闭、经校验的配置字段之后，并把已施加的策略记录在它所产出的简报上。

1. **一个配置字段，默认关闭。** `taskAwarePolicy: false` 经由本包既有的 schemastery `Config` 校验、由 `resolveConfig` 解析，并明确记载为关闭。关闭时注入器不调用任何新代码路径，被注入简报与从未设置该字段的挂载逐字节相同，随包 profile 在运维开启它之前一无所变。
2. **任务类别来自已记录的证据。** 它是某条 usage 记录中列有本会话的技能名（`ctx.evolutionSkillTelemetry`），而这正是 `dsh-evolution-retrieval` 给会话打分的同一任务类别轴；该存储自己的 `gradesOf` 本来就是按这种方式把技能会话连接到任务类别的。一个会话记录了多个技能就有多个类别：它们按名字顺序被逐个询问，越过闸门的最高分推荐胜出。没有遥测存储、存储没有 `recommend`、没有类别列出该会话、没有类别有越过证据闸门的推荐，这四种情况都会回退到本挂载自己的配置，并记 debug 日志。
3. **一条纯决策规则，并如实报告它做不到的部分。** `applyRetrievalPolicy(taskClass, recommendation, escalation)` 返回该轮的各旋钮，外加两份清单。本注入器自己掌握的维度采用推荐值：通道（`graph` 映射为 `graph-first`，`hybrid` 映射为 `both`）、取 `workspace` 时的记忆范围、图深度，以及阈值。其余每一个维度都连同原因记入 `unapplied`——`queryExpansion`、`weights`、`reranker` 与 `mmr` 在这里是已发布的选择，而 `vector` 的来源或 `session`/`global` 的范围则保留本挂载自己的通道与范围。一条注入器只能部分服务的推荐，绝不会被悄悄半途执行。
4. **已施加的策略搭载在简报自身的持久记录上。** 被注入的 `user/message` 携带 `active-memory` 来源；该来源新增一个可选的 `policy` 字段，持有已施加维度、未施加维度、该轮的实际旋钮，以及被推荐配置的规范键。这条消息是一个 surface 事件、持久存在于会话日志中，因此日志无需任何新的持久词汇就能重建该简报出自哪些维度：既不加 `SessionEventMap` 键，也就不用重新生成 `docs/persistence-catalog.md` 与 `packages/core/session/src/known-event-types.ts`——这两者不属于本任务，而它们过期会让 `session-persistence` 直接拒读该日志。
5. **两条可选缝，不是一条。** 读取推荐是第二条结构化缝（`ctx.get('evolutionRetrieval')`，按 `recommend` 守护），与既有的、按 `record` 守护的写入缝并列，因此一个能记录但不能推荐的存储（或反之）仍能提供它拥有的那一半，而策略的缺席绝不影响那条旁路记录。
6. **该步骤的其余部分一无所变。** 同样的节奏、同样的 workspace 范围、同样的融合、同样的渲染与字节预算，而且仍然不调用模型：该策略读取一个存储并计算一个纯函数。

## 考虑过的替代方案

- **一个专用的、仅日志的会话事件（`active-memory/retrieval-policy`）。** 否决：新的会话事件键是持久日志词汇，而它所馈入的持久化目录与运行时已知词汇模块都由 `scripts/gen-persistence-catalog.ts` 生成——不在本任务的归属范围内；而且在它们重新生成之前，新类型无法被读回（`session-persistence` 会拒读未标记的未知类型）。被注入的消息本身就是仓库对模型可见变更所要求的那个会话事件，而插件在自己消息的来源上记录结构化出处是既有的惯例（`agent-instructions`、`time-context`）。
- **从轮次文本、或从路由器的实测类别推导任务类别。** 否决：从提示词文本推断类别是一个背后没有已记录证据的猜测，而 `dsh-evolution-router` 不保存会话到任务类别的关联——它的结果是按路由的，不是按会话的。技能遥测存储是唯一把会话记录到任务类别上的存储，而且它正是推荐本已键定的那根轴，于是两半在构造上就一致。
- **把已施加的配置写进归属记录，而不是写在简报上。** 否决：该存储的模型是每个会话一个配置，为同一个会话写下第二条归属会让该会话的评分计入两个配置。已施加的配置属于某一轮，而简报正是某一轮的记录；README 记下这条归属局限，而不是破坏样本计数。
- **施加 `weights`、`reranker` 或 `mmr`。** 否决：注入器没有这些旋钮——融合是 `dsh-session-query` 内部 `fuseSessionRankings` 的倒数排名求和，该路径上也不存在重排或多样化步骤。为了满足某条推荐而发明一个，会是新的检索机制，而不是既有机制之上的一条策略；这些维度只被报告。
- **在 `searchSessionsHybrid` 内部施加该策略。** 否决：那个入口只接收一个请求，既没有会话也没有任务类别，而且注入器并不调用它——它自己运行两条腿并融合。唯一能知道某轮任务类别的地方就是 pre-step 监听器。
- **为该策略做逐轮存储写入。** 否决，理由同归属记录那条替代方案，且每次检索的轮次都写入会把存储延迟放到轮次路径上，而既有记录刻意不这么做。

## 后果

- 默认关闭时没有任何可观察变化：检索路径、简报文本、以及简报的来源都与之前完全一样，测试通过把一个关闭策略的挂载与一个从未设置该字段的挂载相互比较来钉住这一点。
- 开启后，某个技能记录过的会话所在的轮次会按被推荐的配置检索，其简报携带已施加的记录；回退的轮次不携带，而两者都记 debug 日志，运维因此能区分"没跑的策略"与"跑了但一无所获的策略"。
- 该策略除简报之外不触及任何模型提示词，因此本包仍不发布运行时不变式伴生入口；变化只是日志本就持有的那条消息上多了一个可选元数据字段。
- 注入器新增一个纯模块（`src/policy.ts`），不新增包、域、存储或模型调用。两个源文件都满足仓库的逐文件 100% 覆盖率闸门（228 条语句、110 个分支）。
- 归属记录照旧记录本挂载的配置，而不是某一轮的推荐；两者都运行过的会话只被归属到本挂载的配置。要拆分它需要该存储"每会话一个配置"的模型所没有的逐轮归属，README 已把它记为局限。
- `dsh-session-query` 未被改动：它的 hybrid 入口按请求执行同样的倒数排名融合，而一旦策略落在能知道该轮任务类别的地方，§53 该行剩下的那一半在那里就不需要任何改动。

## 与计划的偏离

计划对已施加的策略是否应成为一个新的、仅日志的会话事件持开放态度。它没有成为事件，出于上述归属原因；该记录改为搭载在被注入消息的来源上。若集成者后重新生成持久化目录，仍可在不改变该策略决策规则的前提下补上一个专用事件。

## 测试

`packages/context/active-memory-context/tests/policy.spec.ts` 在没有 context 的情况下覆盖这条纯规则：注入器自己掌握的维度连同其值进入 `applied`，无法服务的维度连同原因进入 `unapplied`；`graph` 来源映射到 graph-first 通道；`vector` 来源加非 workspace 范围则保留本挂载自己的通道。

`packages/context/active-memory-context/tests/index.spec.ts` 在真实的 pre-step 路径上补充了行为：

- 关闭策略、但有推荐在场的挂载所注入的简报文本与从未设置该字段的挂载逐字节相同，且简报来源完全没有 `policy` 字段；
- 一条 `source: 'graph'`、`graphDepth: 3`、`threshold: 0.9` 的推荐会跳过向量腿的嵌入调用、把图谱展开为三跳而非本挂载的一跳，并把这三个已施加维度连同其余未施加维度记在简报上；
- 推荐的 0.9 阈值会丢弃相似度 0.707、而本挂载自己的 0.5 会保留的命中，而同一挂载在关闭策略时会注入它；
- 一个被四个技能记录过的会话会逐个询问每个类别，并运行最高分的推荐；
- 未挂载的遥测存储、没有任何技能记录过的会话、没有推荐的类别、以及没有 `recommend` 的存储，都会回退到本挂载的配置，并留下说明这一点的 debug 日志。
