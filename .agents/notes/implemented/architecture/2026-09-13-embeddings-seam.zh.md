# Agent Note: 嵌入成为带内容哈希缓存的能力接缝

Status: implemented

[English](2026-09-13-embeddings-seam.md) | 中文

## 问题

规范中的混合检索机制需要向量，而 harness 没有任何产生向量的途径：没有嵌入能力、没有嵌入提供方、也没有缓存，因此每个消费者都只能直接访问后端，并重发它已经发送过的文本。

新增这项能力引出两个规范没有回答的问题。默认值在哪里填充——是没能具名模型的调用方，还是没能具名路由却已注册多个的调用方？又是什么限定了"重复一次纯粹由输入决定的调用"的代价？

第三个问题来自本仓库自身的约定而非规范：一条能力接缝必须交付什么。术语表明确指出，接缝由 Service Definition、一个或多个 Service Provider，以及一个或多个注入该服务的 Consumer 组成；一个包只有在三者属于同一关注点时才可同时承担多个角色。

## 决策

两个包，沿用 `dsh-llm` 及其提供方已确立的形态。

`@deepseek-ai/dsh-embeddings` 是 Service Definition：`ctx.embeddings` 注册提供方路由，并每次调用服务一个批次。`resolve(request)` 是显式的取默认值步骤——省略的路由取唯一已注册者，省略的模型取提供方自身的 `defaultModel`，而已注册多个却省略路由时以 `AMBIGUOUS_PROVIDER` 失败，而不是任选其一。`embed(request)` 服务缓存中已有的文本，只把其余的发给提供方，并同时返回两个计数。

缓存键是解析后的路由、模型与文本三者以不可能出现在任一部分中的字符连接后的 SHA-256，因此改动其中任一项都对应另一条目而非旧向量；命中会重新插入，因此第一个键永远是最近最少使用的那个。上界是 `maxCacheEntries`。

`@deepseek-ai/dsh-embeddings-http` 是 Provider：每批向 `<baseURL>/embeddings` 发一次 POST，后端地址与模型必填——本仓库没有声明自有的嵌入模型——bearer 密钥每批通过凭据接缝解析，因此轮换后的密钥能用于下一次请求。

## 考虑的替代方案

**在定义之上再做一个缓存提供方。** 一个按内容哈希缓存的包装提供方本可以把缓存挡在定义之外。它输在：此后每个提供方都得再加这层包装才能获得该行为，而未包装注册的提供方会悄悄重复嵌入——缓存是这项能力的属性，不是某一种传输的属性。

**把持久缓存放进定义自有的存储域。** 它能跨重启存活。但它也放错了归属：缓存向量的持久对应物是存放该向量的索引，定义级的存储会重复该索引的数据，并在模型变更时需要自己的失效逻辑。进程内缓存覆盖重复调用；持久复用属于存放向量的一方。

**把取默认值放进各提供方。** 提供方本可以自己填好模型与路由。那是在使用点上的隐式 `?? default`，正是本仓库在包边界处禁止的做法；而且会让 `resolve` 在不发起调用的情况下无法回答"这次请求实际跑在什么之上"。

**面向特定厂商、硬编码后端与模型的提供方。** 它会比可配置版本更好读。但它也会凭空造出一个本仓库并未声明的模型名，因此本包刻意假定 OpenAI 兼容格式，面向特定厂商的提供方应当是另一个包，而不是这里的一个分支。

**把提供方偏短的答案截断到较短长度。** 代码选择拒绝；截断会让此后每个文本错位到错误的向量上，那是静默的数据损坏，而不是被报告出来的失败。

## 后果

`ctx.embeddings` 已存在，Definition 与 Provider 均经过测试：两个包共 33 个测试，语句、分支、函数与行覆盖率均为 100%。

缓存是每进程实例的，因此重启会重新嵌入；同一批内的重复文本会全部发送；没有批次大小上限、没有重试、也不校验维度。这些都记录在包 README 中，而不是留作暗示。

**Consumer 尚未构建。** 按术语表自身的定义，在某个消费者注入 `ctx.embeddings` 之前，这条接缝是不完整的。预期的消费者是 `dsh-session-query-sqlite` 中的向量通道：随文档索引写入的 `persisted_vectors` 表、其上的语义检索，以及与既有 FTS5 通道的排名融合。那项工作涉及 schema 版本号提升，以及对一个 1133 行引擎共享索引路径的改动，因此被延期，而不是半途落地。追查过程中发现两项约束：`_replacePersistedSession` 与 `_replaceLiveSession` 是同步的，并运行在串行化的 reconcile 事务内，因此在那里嵌入会让该事务在提供方调用期间一直打开，向量处理必须在事务关闭之后进行；候选查询完全围绕 FTS5 的 `MATCH` 与 `highlight()` 构建，因此语义通道需要一条既不使用 `MATCH` 也不使用 `highlight()` 的并列查询。

消费者缺失并不意味着该服务没有文档：`gen-cordis-catalog` 最初拒绝 `ctx.embeddings`，是因为其签名类型没有文档归属；把这四个类型分类之后，它便渲染在 LLM 子系统页上。那次拒绝是分类缺口，不是可达性问题。

向定义中添加语义方法是对一个在线服务的破坏性改动：`SessionQueryEngine` 有一个生产子类（`SqliteSessionQueryEngine`）和分布在七个包中的七个测试替身，它们都必须同一次改动中实现新方法。在消费者存在之前，这两个包各自正确，但这项能力在仓库内没有调用方。
