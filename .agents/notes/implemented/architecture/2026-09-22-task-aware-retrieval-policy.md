# Agent Note: Task-aware retrieval policy

Status: implemented

English | [中文](2026-09-22-task-aware-retrieval-policy.zh.md)

## Problem

`specs/evolutionary-harness-v11-deep-research.md` §53's Hybrid Search row asks for a "task-aware retrieval policy", and §39 lists the dimensions such a policy would vary: retrieval source, query expansion, weights, reranker, MMR, memory scope, graph depth, and the active-memory threshold. The prior wave built the recording half: [`dsh-evolution-retrieval`](2026-09-22-retrieval-aware-evolution.md) records the configuration each session ran under and recommends the best one per task class above an evidence gate, and `dsh-active-memory-context` records the configuration in force as a side record. Its own note stated the gap in the same breath: "Nothing consumes the recommendation automatically — the injector still runs exactly what its config says."

So a deployment could accumulate per-task-class recommendations and never run one. Two further pieces were missing to close that:

- The injector had no notion of the turn's task class. Guessing one from the turn's text would be exactly the "model-visible ⟺ logged" violation the repository avoids: a policy decision with no recorded evidence behind it.
- Nothing durable said what a turn actually retrieved under. Two sessions briefed under different configurations were distinguishable in the attribution table, but a single session whose turns ran recommended configurations was not.

## Decision

Make `dsh-active-memory-context` consult the recommendation for the turn's task class, behind a validated config field that ships off, and record the applied policy on the brief it produced.

1. **One config field, off by default.** `taskAwarePolicy: false` is validated through the package's existing schemastery `Config`, resolved by `resolveConfig`, and documented as off. With it off the injector calls no new code path, the injected brief is byte-identical to a mount that never set the field, and the shipped profile is unchanged until an operator turns it on.
2. **The task class comes from recorded evidence.** It is a skill whose usage record lists this session (`ctx.evolutionSkillTelemetry`), which is the same task-class axis `dsh-evolution-retrieval` grades a session on; the store's own `gradesOf` already joins skill sessions to task classes that way. A session that recorded several skills has several classes: they are consulted in name order, and the highest-scoring recommendation above the gate wins. No telemetry store, no `recommend` on the store, no class listing the session, and no class above the evidence gate all fall back to the mount's own configuration, debug-logged.
3. **One pure decision rule, and it reports what it cannot do.** `applyRetrievalPolicy(taskClass, recommendation, escalation)` returns the turn's knobs plus two lists. The dimensions this injector owns take the recommended value: the lane (`graph` maps onto `graph-first`, `hybrid` onto `both`), the memory scope when it is `workspace`, the graph depth, and the threshold. Every other dimension is recorded in `unapplied` with the reason — `queryExpansion`, `weights`, `reranker` and `mmr` are the shipped choices here, and a source of `vector` or a scope of `session`/`global` leaves the mount's own lane and scope in place. A recommendation the injector can only partly serve is never silently half-run.
4. **The applied policy rides the brief's own durable record.** The injected `user/message` carries an `active-memory` source; that source gains an optional `policy` field holding the applied dimensions, the unapplied ones, the turn's effective knobs, and the recommended configuration's canonical key. The message is a surface event, durable in the session log, so the log reconstructs which dimensions produced the brief without a new durable vocabulary: no `SessionEventMap` key, and therefore no regeneration of `docs/persistence-catalog.md` and `packages/core/session/src/known-event-types.ts`, which this task does not own and whose staleness would make `session-persistence` refuse the log outright.
5. **Two optional seams, not one.** Reading the recommendation is a second structural seam (`ctx.get('evolutionRetrieval')` guarded for `recommend`) beside the existing write seam guarded for `record`, so a store that records but cannot recommend — or the reverse — still serves the half it has, and the policy's absence never affects the side record.
6. **Nothing else about the step changes.** The same cadence, the same workspace scope, the same fusion, the same rendering and byte budget, and still no model call: the policy reads one store and computes one pure function.

## Alternatives considered

- **A dedicated log-only session event (`active-memory/retrieval-policy`).** Rejected: a new session-event key is durable log vocabulary, and the persistence catalog and the runtime known-vocabulary module it feeds are both generated by `scripts/gen-persistence-catalog.ts` — outside this task's ownership, and a new type is not readable back until they regenerate (`session-persistence` refuses an unmarked unknown type). The injected message is itself the session event the repo requires for a model-visible change, and a plugin recording a structured source reference on its own message is the existing idiom (`agent-instructions`, `time-context`).
- **Deriving the task class from the turn's text, or from the router's measured classes.** Rejected: inferring a class from prompt text is a guess with no recorded evidence behind it, and `dsh-evolution-router` keeps no session-to-task-class link — its outcomes are per route, not per session. The skill-telemetry store is the one store that records a session against a task class, and it is the axis the recommendation is already keyed on, so the two halves agree by construction.
- **Recording the applied configuration into the attribution instead of the brief.** Rejected: the store's model is one configuration per session, and writing a second attribution for the same session would count that session's grade for two configurations. The applied configuration belongs to a turn, and the brief is the record of a turn; the README states the attribution limitation rather than corrupting the sample counts.
- **Applying `weights`, `reranker`, or `mmr`.** Rejected: the injector has no knob for them — the fusion is `fuseSessionRankings`' reciprocal-rank sum inside `dsh-session-query`, and no reranker or diversification step exists in the path. Inventing one to satisfy a recommendation would be a new retrieval mechanism, not a policy over the existing one; those dimensions are reported instead.
- **Applying the policy inside `searchSessionsHybrid`.** Rejected: that entry point takes a request and has no session and no task class, and the injector does not call it — it runs its own two legs and fuses them. The only place a turn's task class is knowable is the pre-step listener.
- **A per-turn store write for the policy.** Rejected for the same reason as the attribution alternative, and because a write on every searching turn would put storage latency on the turn path where the existing record deliberately does not.

## Consequences

- Off by default, nothing observable changes: the retrieval path, the brief text, and the source of the brief are exactly what they were, which the tests pin by comparing a policy-off mount against a mount that never set the field.
- On, a turn whose session some skill recorded retrieves under the recommended configuration and its brief carries the applied record; a turn that fell back carries none, and both are debug-logged so an operator can tell a policy that did not run from one that ran and found nothing.
- The policy reaches no model prompt beyond the brief it already reached, so the package still publishes no invariant companion; what changed is one optional metadata field on a message the log already holds.
- The injector gains one pure module (`src/policy.ts`) and no new package, domain, store, or model call. Both source files hold the repository's per-file 100% coverage gate (228 statements, 110 branches).
- The attribution keeps recording the mount's configuration, not a per-turn recommendation; a session that ran both is attributed to the mount's alone. Splitting it needs per-turn attribution the store's one-configuration-per-session model does not have, and the README states it as a limitation.
- `dsh-session-query` is untouched: its hybrid entry point performs the same reciprocal-rank fusion on request, and nothing in the §53 row's remaining half needed a change there once the policy lived where the turn's task class is known.

## Deviations from the plan

The plan left open whether the applied policy should be a new log-only session event. It is not, for the ownership reason above; the record rides the injected message's source instead, and an integrator who regenerates the persistence catalog can still add a dedicated event later without changing the policy's decision rule.

## Testing

`packages/context/active-memory-context/tests/policy.spec.ts` covers the pure rule without a context: the injector-owned dimensions land in `applied` with their values and the unservable ones in `unapplied` with their reasons, a `graph` source maps onto the graph-first lane, and a `vector` source with a non-workspace scope leaves the mount's own lane in place.

`packages/context/active-memory-context/tests/index.spec.ts` adds the behavior on the real pre-step path:

- a policy-off mount with a recommendation present injects a brief whose text is byte-identical to a mount that never set the field, and a brief source with no `policy` field at all;
- a recommendation of `source: 'graph'`, `graphDepth: 3` and `threshold: 0.9` skips the vector leg's embedding call, expands the graph three hops instead of the mount's one, and records all three applied dimensions plus the unapplied rest on the brief;
- a recommended threshold of 0.9 drops a 0.707 similarity hit that the mount's own 0.5 keeps, while the same mount with the policy off injects it;
- a session recorded under four skills consults every class and runs the highest-scoring recommendation;
- an unmounted telemetry store, a session no skill recorded, a class with no recommendation, and a store with no `recommend` each fall back to the mount's configuration with the debug line that says so.
