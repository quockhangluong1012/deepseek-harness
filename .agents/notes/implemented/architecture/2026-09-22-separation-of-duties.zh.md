# Agent Note：进化角色的职责分离

Status: implemented

[English](2026-09-22-separation-of-duties.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` §53 的 Multi-Agent 一行要求「职责分离 + 专家角色」，而仓库只记录了其中的模型那一半。`evolution-model-routes` 把 §28 的拓扑读作路由——哪个 provider/model 服务哪个角色，并用 `conflicts` 点名一条既产出工作又评判工作的路由——`evolution-evaluator-strategy` 则把 §28 的独立性规则读作模型：`judgeIndependence` 把来自候选自身模型的判定称为 `same-model`，并让它不计入任何佐证。两者比较的都是模型，而 §26 把其 Level 3–5 的元进化押在强治理之上，这种治理最薄弱的一环正是一个无法归属到不同身份的决定。

身份是另一条轴。两条路由可以是两个模型，却仍可能是同一个行动者：一个运维者跑两个模型，一个代理填两个角色。§53 的职责分离说的是这个行动者，而没有任何东西记录某一次运行中哪个身份填充了哪个进化角色，因此也就没有任何东西能据此事由拒绝一个决定。候选的提案者与晋升者可以是同一身份，而各存储仍会报出一场干净、看似独立的晋升。这样的拒绝一旦写下，就绝不能被「缺失」满足：一次两种身份都没记录的运行并不因此就是分离的。

## 决定

1. **职责记录在已经拥有角色拓扑的那个存储上，且这些角色不获得任何人设。** `evolution-model-routes` 的域增加第三张表 `duties`，以运行+角色为键，存放 `{ runId, role, identity, at }`；`recordDuty({ runId, role, identity })` 写入一次填充，并替换同一次运行中被重复记录的角色；`duties(runId)` 按 §28 拓扑顺序列出该次运行的全部填充。五个角色就是 `EVOLUTION_ROLES` 已经给出的那些；不定义任何代理人格，也不调用任何模型。
2. **规则是纯函数，且正是 §53 所述的那条。** `separationOfDuties(duties, runId, decision)`（`src/duties.ts`）解析 `SEPARATED_DUTIES` 指派给该决策的角色对——`promotion` 把候选生成与晋升审查配对，`verdict` 把候选生成与评估配对——读取两个已记录身份，返回 `{ allowed: true }` 或一条拒绝。`same-identity` 携带该身份与两个角色：`identity 'agent-a' filled both candidate-generation and promotion-review for run 'run-1'`。`unknown-identity` 点名没有记录的角色。该规则把职责作为参数，因此 §53 的策略是单元测试的对象而不是宿主夹具。
3. **未记录的角色失败即关闭。** 缺失的行与空身份都被读作未记录，并以 `unknown-identity` 拒绝，因为该规则回答的问题是「是否已证明两个身份不同」，而缺失什么也证明不了。`judgeIndependence` 把同样的空值读向另一边——空的评判模型不是自我评判的判定——这正是注释一个已记录判定与拒绝一个决定之间的区别。
4. **拒绝是存储自己的检查，并被明确记录为未强制。** `checkDuties(runId, decision)` 就是该规则作用在存储自己的行上。本仓库没有任何晋升路径查询它：做出晋升决定的两条路径是 `dsh-command-evolution` 的 `/canary promote <id>` 与执行器的发布监视器（`canary.advance(id, 'promoted')`），两者都不记录任一角色的身份。本包不去假装把守一条自己并不拥有的路径，而是在 README 的限制中写明这条拒绝目前没有调用方。
5. **职责键是路径安全且单射的。** `dutyKey(runId, role)` 用 `_` 连接两者，而任何角色字面量都不含 `_`，因此没有两组 (run, role) 会碰撞，且该键满足按记录布局的 `[a-zA-Z0-9_-]+` 键规则。既有的 `routeKey` 用 `\0` 连接 provider/model，并不满足它——见「途中发现的修复」。
6. **域保持版本 1。** 在按记录域的既有单元中，新增的表读作空表，且没有任何版本 1 记录改变形状，因此新增表不需要 `compatibleVersions` 条目。
7. **此处没有任何东西进入模型提示词，因此没有新的会话事件。** 身份就是调用者记录的内容；存储不观测任何会话、代理或运维者，也不调用任何模型。

## 考虑过的替代方案

- **每次运行一条记录，内部存放角色→身份的映射。** 拒绝：记录一个角色会变成对该行的读-改-写，因此同一次运行中两个并发填充不同角色可能丢失其一；而角色映射所需的偏记录模式也比本包已为 `routes` 使用的复合键需要更多机械。
- **把未记录的角色读作不同身份。** 拒绝：这会让拒绝可被「省略」满足——正是 §53 的规则要捕捉的失败模式——并会让从不记录职责的部署依据看似分离的证据晋升。
- **让 `conflicts()` 承担拒绝。** 在 `2026-09-22-judge-independence-and-defenses.md` 中已为路由读数拒绝过：运维者的固定指派按设计优先于拓扑。路由冲突与职责冲突也是不同的问题——两个不同模型可以是同一个身份，两个身份也可以共用同一个模型。
- **在本次改动中直接强制于晋升路径。** 不可得：两个调用点都位于本包之外，且都不携带任一角色的身份；而从晋升本身合成一个身份，会把晋升者记成它自己的审查者或记成陌生人，两者都不是证据。
- **单独建一个治理包。** 拒绝：角色词汇与该次运行的路由记录已经住在 `evolution-model-routes`，第二个存储会分叉 `EVOLUTION_ROLES`，让拓扑有两个所有者。
- **对职责键做哈希或转义。** 拒绝：没有任何东西要反解该键，角色是不含分隔符的封闭词汇，而哈希会把运行身份藏在介质里，让运维者读不到。
- **做一次模式迁移式的版本提升。** 拒绝：在版本 1 的单元里，新增表是「不存在」而不是「过期」，因此丢弃可读的 `routes` 与 `evidence` 记录只会白白损失证据。

## 后果

- `evolution_model_routes` 现在在 `routes` 与 `evidence` 之外持有 `duties` 表；重启会通过同一份 zod 规范把填充读回来，每次填充都是一次持久写入，没有读-改-写窗口。
- `checkDuties` 返回裁决而不是抛出：做出决定的调用者负责呈现该拒绝，而 `same-identity` 的理由就是为让运维者读到的那个句子而写。
- 在一条既知道谁提案又知道谁审查的晋升路径调用它之前，这条拒绝只是建议性的。在此之前，§58.12 的「只记录不强制」边界对这套机制同样成立；而从不调用 `recordDuty` 的部署对每一次运行都会得到 `unknown-identity`，而不是被猜测的裁决。
- 职责键的角色一半按构造即路径安全；运行 id 仍需路径安全，按记录的 JSON 布局会在写入时响亮拒绝不安全的 id，而不是丢弃该记录。
- `verdict` 为 §53 的评估那一半做好了记录与检查，而无需改动 `evolution-evaluator-strategy`——它保留对已记录判定的模型级 `judgeIndependence` 读数。

## 测试

`packages/evolution/evolution-model-routes/tests/duties.spec.ts` 在没有上下文的情况下固定该规则：两个决策在身份不同时放行、在身份相同时拒绝且理由点名两个角色；未知拒绝的两个方向；空身份读作未记录；另一次运行的职责不予计入；以及键格式。`tests/store.spec.ts` 驱动真实存储：每次运行每个角色一个身份并按拓扑顺序排列、被重复记录的角色替换其身份而不是新增一行、另一次运行的填充不混入、一次晋升所走的「未知→冲突→放行」序列、为 `verdict` 读取评估配对、跨重启经 zod 规范的持久性，以及存储启动前读取即抛出。`src/duties.ts` 的每个分支都被覆盖。

`README.md` 与 `README.zh.md` 都加入了职责 API、§53 章节与两条限制，并重新记录了配对。

## 途中发现的修复

未修复，且值得单独一次改动：本包的 `routeKey`/`assignmentKey` 用 `\0` 连接 provider/model，而按记录布局的 `[a-zA-Z0-9_-]+` 键规则会拒绝它，且 base 配置让 `storageDomain` 跑在 `backend: json` 上。用 `JsonStorageBackend` 启动真实存储时，`observe` 与 `pin` 都以 `per-record key 'candidate-generation\0p\0m' is not path-safe` 失败；优化器把它吞成一条警告，因此在 JSON 后端的宿主上路由证据什么都没记录。`evolution-evaluator-strategy` 的 `strategyKey` 形状相同。新的 `duties` 表不是这样，这正是它的键格式与其姊妹键不同的原因。修复需要一次编码决策——仅换一个安全分隔符还不够，因为像 `llama-3.1-70b` 这样的模型 id 含有布局会拒绝的字符。

## 未触碰之处

此处没有任何东西改变会话所见、收下某个基准任务或开启一次评估：存储记录填充并回答一个目前无人读取的检查，执行器的各个循环未被触碰。本包在组 README 中的那一行与生成的 Cordis API 目录仍然描述加入职责之前的表面；两者都在本次改动的所有权之外，且目录是生成器的产物。
