# Agent Note: Agent kernel control plane

Status: implemented

[English](2026-09-16-agent-kernel-control-plane.md) | 中文

## Problem

Harness 记录了发生了什么，却没有记录决定了什么。会话日志保存轮次、步骤、工具调用与结果，而 `sandbox-policy`、`user-approval`、`permission-presets` 与 `guard/budgets` 各自决定权限的一个切片——但没有任何东西能从持久证据回答：某个任务原本要做什么、这些决策中哪些适用于某一次具体工具调用，或者某个完成声明是否曾被验证过。这些缺口是结构性的，而不是缺失的功能：没有规范的任务契约，没有把策略决策与组合出它的沙箱和人类应答者连接起来的单一记录，也没有一个能够拒绝无证据支撑的 "完成" 的完成门禁。

## Decision

新增一个可选加入的包 `packages/runtime/agent-kernel`，它观察循环已经发布的 waterfall 与事件，并记录它所组合出的决策。它不拥有任何执行。

Kernel 挂载到五个既有接缝上。`agent/created` 把委派回执写入子级会话自己的日志——在双方拥有任务之前——并在父级日志上留一份审计副本。`agent/pre-step` 在首个被接纳的步骤开启任务契约并把它迁移到 `executing`；`tools/pre-execute` 在求值之前追加动作提议，随后追加规则决策、组合后的授权与任何能力授予；`tools/post-execute` 追加带治理记录的动作回执；`agent/turn-stopping` 记录观察边，并在任务声明了必需验收标准时运行完成门禁。

每条记录都是一个持久会话事件，Kernel 的读模型是在一个按会话游标之后对这些事件的折叠，因此重放的日志会重建同一个视图。`mode: 'shadow'`（默认）记录每个决策并原样返回 waterfall；`mode: 'enforce'` 返回 `deny` 以拦下调用，返回 `ask` 以把它路由到工具注册表已经拥有的已组合应答链。

四个决策保持分开，因为所有者保持分开。权限文档针对已声明能力与资源 glob 决定 `allow`、`ask` 或 `deny`。`SandboxPolicyService` 仍是技术边界的唯一解析者，它拒绝的写入能力会被拒绝而非询问。子 agent 的委派回执接着求交：父级从未授予的能力、可写范围或深度会被拒绝，无论规则或状态说什么，每个子级授权都记下它所依据的回执。`ApprovalService` 仍是唯一的交互式应答者，通过注册表的 `ask` 路径抵达，而 Kernel 观察由此产生的 `approval/asked` 与 `approval/decided` 事件来填充回执，而不是自己去询问。

任务创建发生在首个被接纳的步骤，而不是 `agent/session-start`。只有在某个步骤认领人类消息之后目标才可知，而 session-start 处的追加会落在打开的轮次之外，持久日志在那里无法把它与崩溃残尾区分开。

被组合策略拒绝的动作被记录为 `outcome: 'denied'`，绝不记录为工具失败，因此读取者能把"Harness 说了不"与"工具运行后坏了"区分开。

## Alternatives considered

**把 agent 循环分叉成一个任务感知的驱动器。** 拒绝：`core/agent-loop` 拥有轮次与步骤的生命周期、取消与工具并发，第二个驱动器会复制所有这些。Kernel 需要的每个集成点都已经作为 waterfall 或事件存在，而规范自身的不变量禁止替换循环。

**默认强制执行。** 拒绝：一份从未在真实流量上运行过的权限文档会拒绝错误的东西，而默认开启强制执行会在工具尚未声明能力的部署中停下每一次工具调用。默认是 shadow 模式，因此部署先度量，后治理。

**在 Kernel 内直接调用 `ApprovalService` 来决定 `ask`。** 拒绝：工具注册表已经通过已组合的应答链解析 `ask`，并在没有可用应答者时按失败关闭。再次调用该服务会为一次调用两次询问人类，并复制注册表的取消处理。

**把权限文档建模成工具名允许列表。** 拒绝：工具名不是能力。同一个工具针对一种资源是安全的，针对另一种可能危险，而基于名字的列表无法表达工作区边界、shell 命令或主机——这些正是 `capabilities.register()` 从参数投影出来的。

**在 `agent/session-start` 创建任务。** 拒绝，理由同时基于目标与持久性两点，已记录在 Decision 之下。

**在每个工具包里声明能力。** 拒绝：产品工具包将依赖策略平面，而工具包必须在没有 Kernel 时也可挂载。独立的可选 builtins 插件把词汇、注册表与已发布声明收拢在一个平面，而目录覆盖 spec 从工具包自己喂给的生成器重新推导工具清单。

**在每次子级动作时重新解析父级会话。** 拒绝：回执正是在创建时写入子级自己的日志，好让重放无需父级会话就能重建子级权限。按动作重新解析会让每个子级授权依赖一个可能早已卸载的会话，并让后来的父级状态改写早前动作所依据的权限。

## Consequences

Kernel 为部署提供一份持久任务契约、每次工具调用一条可归因记录，以及一个拒绝无支撑声明的完成门禁。代价是在挂载它的每个会话中每次工具调用增加一条审计记录，并且它持有一个按会话的折叠游标，其内存随 Kernel 事件数量而非日志长度增长。

它划出的边界刻意狭窄。内置工具由独立的可选 `agent-kernel-builtins` 插件声明，而不是由工具包声明，因为只有策略平面可以扩展权能词汇；重命名了工具、铸造了 `mcp__*` 或 `structured_output` 名字、或自带了工具的部署自行声明那些。委派回执的严格程度不超过签发它的文档，而解析不到父级会话的子级回退到部署上限。它不附带标准验证器，也不附带崩溃恢复扫描器，因此必需的验收标准在验证器注册之前保持 `unknown`。这些缺口记录在包 README 的已知限制中，而非被隐藏。

`packages/runtime/agent-kernel/tests` 钉住这些行为：状态机边表及其 revision 守卫、权限引擎的优先级与沙箱组合、能力注册表的替换规则、恢复表、完成门禁与标准验证器注册表、账本折叠（含游标复用与失败解决）、Kernel 自身的 intake、授权、commit、验证、附着与检查点路径、子级创建时的委派签发及其能力、范围与深度交集（含冷子级与继续子级路径），以及一次启动 `cordis.yml` 的真实 Loader 组合，证明强制执行模式与文档校验是配置而非常量。`packages/runtime/agent-kernel-builtins/tests` 钉住声明：每条都可解析、每份投影都全函数、该表恰好命名了生成的工具目录所列的工具，以及一次 enforce 模式运行证明已声明的内置工具可以执行。
