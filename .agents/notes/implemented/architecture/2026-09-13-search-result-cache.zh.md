# Agent Note：搜索结果获得有界、按世代加键的 TTL 缓存

Status: implemented

[English](2026-09-13-search-result-cache.md) | 中文

## 问题

规范 §16.2 把两件事捆绑进一个 Python 类里描述：持久化索引被复用而非每次搜索都重建，以及有界 TTL 的搜索结果缓存，二者由一个 `index_health` 状态机（`healthy`/`dirty`/`rebuilding`）门控，决定是搜索当前索引、触发后台重建，还是阻塞等待重建。

前一半在本次变更之前已经是本包的设计。派生 SQLite 索引跨重启持久化，并增量对账：`_reconcile` 把每个会话的持久化修订与已索引的行比较，只重新读取发生变化的部分，在每次搜索的一个串行化事务内完成。它从不从零重建，因此不存在与 `index_health` 对应的东西——索引因构造方式而始终是最新的，而不是在惰性重建之后最终变新。在这里加一个健康状态机，等于是在解决一个本包并不存在的陈旧性问题。

真正缺失的是第二半——缓存重复的相同搜索。

## 决定

`@deepseek-ai/dsh-session-query-sqlite` 增加了一个有界、带 TTL 的 `searchSessions`/`searchEvents` 页缓存（`src/result-cache.ts`，`SessionResultCache`）。规范化查询、页码与语料世代都相同的重复请求会直接从内存作答，而不重新运行 SQLite。两个新的 `Config` 字段——`resultCacheEntries`（默认 1000）与 `resultCacheTtlMs`（默认 3,600,000，即一小时）——像本包中其它每一个可调参数一样受约束：用经过校验的 `Config` 字段约束，绝不硬编码常量。

### 缓存键携带语料世代

引擎已经为每个语料维护一个单调递增的世代（整个语料 `searchSessions` 作用域用 `_globalGeneration`，单个会话的 `searchEvents` 作用域用 `target.generation`），以便分页游标能检测到语料变化并以 `SESSION_QUERY_STALE_CURSOR` 失败，而不是悄悄返回指向另一个语料的偏移量。

结果缓存把同一个世代当作其键的一部分复用： `` `sessions|${fingerprint}|${generation}|${offset}|${limit}` `` 与 `` `events|${fingerprint}|${target.generation}|${offset}|${limit}` ``。 语料变化会递增世代，从而改变每一个受影响的键，因此在结构上不可能提供陈旧的页——不存在可能被遗忘、或与并发写入产生竞态的失效步骤。

### 边界

- `maxEntries`（LRU）：一旦 map 超出该边界，最久未被触碰的条目被淘汰。默认 1000， 对应规范参考实现 `TTLCache(maxsize=1000)`。
- `ttlMs`：条目只在写入后的这么多毫秒内可以作答，无论世代是否变化。默认 3,600,000 （一小时），对应规范参考实现 `ttl=3600`。
- `close()` 时缓存与它现在遮蔽的 SQLite 句柄一起被清空。

## 考虑过的替代方案

**按请求缓存，并在每次写入时显式清除条目。** 否决：那需要缓存知道每一条会修改语料的代码路径，并且每一条都不能出错；而按世代加键则让这整类 bug 变得无法表示。

**只用 TTL 的缓存——也就是规范参考实现的形状（`TTLCache(maxsize=1000, ttl=3600)`）。** 否决：只按请求加键时，语料变化不会改变键中的任何东西，因此一次恰好在写入之前被缓存的页会一直作答到 TTL 到期，最长可达一小时。既有的世代会在语料变化时改变每一个受影响的键，这才使得提供陈旧的页在结构上不可能。

**照搬规范里的 `index_health` 状态机。** 否决：`_reconcile` 已经让索引在每次搜索时因构造方式而保持最新，因此没有任何陈旧性需要经过 `healthy`/`dirty`/`rebuilding` 这些状态——这个状态机、它的后台重建以及它的阻塞式重建路径，全都是在为一个本包并不存在的问题造机械。

**只按世代加键，去掉 `ttlMs`。** 就本记录自身的说法否决：正确性不会变，因为同一世代的键因构造方式就是最新的；但规范参考实现在 `maxsize=1000` 之外还带有 `ttl=3600` 这第二重边界，而这里两个默认值都对应它——去掉 TTL 会让条目寿命只能顺带地由 LRU 淘汰来约束。

## 后果

- 重复的相同请求直接从内存作答，而不重新运行 SQLite，引擎可观察到的答案也没有变化：语料变化会移动每一个受影响的键，因此被缓存的页只有在仍然是该语料当下会产出的那一页时才会被送出。
- 不存在可能被遗忘、或与并发写入产生竞态的失效步骤——缓存继承了分页游标本就依赖的世代不变量，因此一次未能递增世代的修改会同时破坏分页。
- 内存由 `resultCacheEntries`（LRU，默认 1000）约束，条目在 `resultCacheTtlMs`（默认 3,600,000 毫秒）之后过期，两者都是经过校验的 `Config` 字段而非硬编码常量；`close()` 时缓存与它现在遮蔽的 SQLite 句柄一起被清空。
- 索引因构造方式始终是最新的——每次搜索都跑 `_reconcile`，没有 `index_health`，也没有后台或阻塞式重建——因此本包不携带任何需要缓存去协调的陈旧性状态。

## 验证

- `tests/result-cache.spec.ts`：`SessionResultCache` 的纯单元测试（未命中、TTL 过期、 LRU 淘汰、覆写、clear）；引擎级测试证明重复的相同搜索不会重新运行底层 SQLite 查询 （用 `vi.spyOn` 监视私有的 `_querySessions`/`_queryEvents` 方法——TypeScript 的 `private` 只在编译期起作用，因此这是在不引入生产测试钩子的前提下观察内部调用次数的 合理方式），以及语料变化会立即体现，而不是提供一个早于该变化的页。
- `tests/sqlite.spec.ts`：在既有的 Cordis `Config` 校验测试中扩展了两个新字段的默认值、 配置值与边界。
