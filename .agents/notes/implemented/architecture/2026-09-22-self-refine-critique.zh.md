# Agent Note：后台评审器中的自我精炼批评

Status: implemented

[English](2026-09-22-self-refine-critique.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` 的 §5 固定了推理时的 `请求 → 草稿 → 批评 → 修订` 环，§53 的 Background Review 一行要求以窄工具做结构化的失败与模式分析。仓库此前只有草稿，没有这个环的后半。

`@deepseek-ai/dsh-evolution-reviewer` 本就在每个回合做一次受门控的提取，而它的协议只回答 `confirms`、`contradicts` 或 `new`——都是关于作用域已存工件的决策。它的笔录只承认人类与助手消息，因此失败的工具调用至多以散文形式抵达模型；它缓冲到的失败结果只用于产出索引。一个出错的回合因此只产出关于事实的经验，不产出对回合本身的批评，而模型本可就该回合说出的更正策略从未被记录到任何地方。

[`evolution-feedback`](2026-09-22-failure-memory-reflection.zh.md) 也不是那一半：它为每条被判定为 `trigger_review` 的信号，依据台账自身的复现证据撰写确定性的结构化反思，既不用模型，也不看任何单个回合的草稿。

## 决定

评审器那唯一一次按回合的模型调用如今同时承载 §5 环的两半。

### 草稿是本回合加上它记录到的失败

缓冲回合时，块为错误的 `tool/result` 会追加一行 `tool` 笔录，形如 `<工具名>: <记录到的结果文本>`；当该结果没有可读文本时依次退回其错误码，再退回 `<工具名> failed`。该行加入的正是组装笔录所用的那份承认行数组，因此它与其他行一起受字节上限约束、一起参与工件与回合文本的相关性排序，并作为回合自身的证据而非第二条输入通道抵达模型。

这没有拓宽任何东西。失败结果本就按回合缓冲用于产出索引，其文本受工具自身输出上限约束，而该行只携带工具名与记录到的结果——从不携带失败调用的参数，那些参数可能含文件正文与凭据，而 §4.2 的 `what_failed` 也并不要它们。评审器依旧不开放任何工具面：该调用根本不宣称任何工具。

### 批评是同一次回答里的第四个动作

笔录含有 `tool` 行的回合可以追加 `{"action":"critique","expectation":…,"failure":…,"correction":…,"confidence":…,"scope":…}`——即 §4.2 的 `violated_expectation`、`what_failed` 与 `corrected_strategy`，外加该修订的 confidence 与 scope。它出现在模型本就用来作答的那个数组里，因此受门控回合仍然只花费一次调用、一份提示、一份输出预算，也没有任何会话日志中本不存在的新输入抵达模型：失败行就是会话自身的 `tool/result` 事件，工件 statement 本就在那里。

这三个具名字段在线上边界是 `z.string()` 而非 `.min(1)`。这是有意为之：模型无法给出依据的批评应当只牺牲自己，而不牵连它所在的那一批。两道闸门都设在评审器而非解析器里：该次调用发出的笔录必须含有一行 `tool`，且该批评必须把三个字段都写明。任一闸门不过的批评会被丢弃并告警，而它旁边的每条决策仍然生效。

### 修订的两半都被记录

被接纳的批评按它闭合的环的阶段各记录一次：

- **批评本身**成为作用域上下文条目，标签为 `Critique: <sessionId>`，其文本写明期望、失败与更正。它像任何上下文条目一样经作用域的简报抵达后续回合，而存储摘要涵盖上下文条目，因此该注入可从会话日志重建。即便 `writeApproval` 把旁边的决策暂存待批，它也直接写入，与召回条目同理：它是评审器对已记录回合自身的解读，而不是对已存工件的变更提案。被存储拒绝时只告警，整批不受影响。
- **它授权的修订**作为一条普通 `new` 候选在该批中同行：以更正为 statement、以失败为 `conditions`、以 `inference` 为 evidence——该更正是模型的解读，而非实测事实——并采用模型自己给出的 confidence 与 scope。正因为它与别的决策无异，`writeApproval` 会暂存它，`/memory approve` 会应用它，合并解析会判定它是否在重述已存事实，超额重试也能丢弃它。

重建永不产出批评：它的材料是从历史中选出的承认行，没有 `tool` 行，因而没有可据以撰写的失败记录。

## 考虑过的替代方案

**为批评增加第二次模型调用。** 这样可以不动提取协议，也让批评拥有自己的提示。已否决：为了重读一份已在提示中的笔录而让每个受门控回合的成本翻倍，而且 §5 的精炼是对一份草稿的一次局部通过；第二次调用还得为同一个回合另配路由、超时、来源与失败故事。

**为批评新建存储或域。** 一张按会话与回合键控的 `evolution_critique` 表能把该环显式记录下来。已否决：`evolution-memory` 已经持有批评成为批评所需的两样东西——持久指引（经验工件）与简报渲染的材料（`contextItems`）。再加一个域还要为它单配摘要参与、容量核算，以及一个尚不存在的读者所需的界面。

**只记经验，丢掉批评记录。** 一次写入而非两次。已否决：§4.2 的词汇正是关键——经验工件只有 statement 与 conditions，装不下"被违背的期望"与"失败"与"更正"三者并列，该环将变得不可观测：读者无法把批评派生的更正与任何别的 `new` 配对区分开。

**把批评记为 episodic 笔记。** Episodic 笔记是作用域的原始整合材料，没有独立于 ttl 的身份。已否决：它们不在简报里、不抵达后续回合，还会被保留窗口剪除——与 §4.1 要求的、供后续回合检索的纠正启发式正好相反。

**在 schema 里要求三个字段。** 对 `expectation`、`failure` 与 `correction` 用 `.min(1)` 能在线上边界强制执行 §4.2，并省掉评审器的闸门。已否决：解析器会拒绝整份回答，于是无据的批评会连同该回合的确认与反驳一起被丢弃，这与其它任何畸形决策所受的宽容正好相反。

**把失败调用的参数放进笔录。** 这样除了结果还能看到尝试本身。已否决：参数携带文件正文、凭据，以及一次失败写入的全部内容；`what_failed` 所需的是记录到的结果加上回合自身的文字，而读取参数会让评审器的笔录成为整条流水线中最宽的模型可见输入。

**用 `evolution-feedback` 的反思为批评提供依据。** 评审器可以为同一个失败读取已判定的信号，而非回合自身的结果。已否决：为一项它亲自观测到的事实而把该流程拓宽到第二个存储，而且两者是不同层次上的不同机制：§4.2 的台账派生反思是作用域级的复现证据，而这里的批评是一个回合的草稿读回自身。

**用一个新配置字段给失败文本设界。** 一个 `maxFailureRowBytes` 能让该行独立于笔录预算受界。已否决：没有引入任何随部署而变的阈值——工具结果由工具自身的输出上限界定，`maxInputBytes` 一如既往界定组装后的请求。新字段还会为一个已存在两处的界再加一行目录。

## 后果

- 每个受门控回合仍然只花费一次模型调用。没有失败工具结果的回合在提示、回答、节奏与成本上都不变：不存在 `tool` 行，笔录与从前逐字节相同，而即便如此到来的批评也会被丢弃。
- 出错回合的提示因工具结果记录到的内容而变长。这是获得有据批评的代价，它受工具上限与笔录字节预算约束，而后者优先丢弃最旧的行——因此较早的失败可能落在长回合之外，从而得不到批评。
- 批评是简报内容。它与任何附加条目一样占用作用域上下文名册与容量，因此在已填满 `maxContextItems` 的作用域上，修订会被记录，而批评条目只告警并被丢弃。
- 评审器仍然不拥有任何域。`CRITIQUE_LABEL_PREFIX` 命名该条目，存储的记忆记录是唯一的持久副本，因此本包依旧不发布 invariant 伴生包。
- 每个批评条目都会改变作用域摘要，从而重新注入简报。一个回合里的两条批评就是两个条目，而一个含多个失败调用的回合可以增加多个。
- 修订的 `evidence` 恒为 `inference`。更正是模型对下一步该做什么的提议，把它记为 fact 或 observation 等于宣称一份它并不具备的测量。

## 测试

`packages/evolution/evolution-reviewer/tests/protocol.spec.ts` 固定第四个动作、提示中的两句话，以及使闸门成立的那条边界：未填写的批评能与一条有效决策一起被解析，而缺少 confidence 或 scope 的批评会拒绝整份列表。

`packages/evolution/evolution-reviewer/tests/reviewer.spec.ts` 在真实的内存记忆存储上端到端固定该环：带失败结果的回合以 `user`/`assistant`/`tool` 三种行抵达，并产出一个写明三个字段的批评条目，外加一个以更正为 statement、以失败为 conditions、`inference`、模型的 confidence 与 scope、以及提取会话为 source 的经验工件；没有失败结果的回合会丢弃同样的批评、存储它旁边的决策，且仍然只调用一次、笔录保持两行不变；三种"有一个字段未写明"的变体都不记录任何批评条目与经验；没有可读文本的失败结果退回其错误码，而调用从未被观测到的失败结果则退回工具名的缺失与空明细；上下文名册已满的作用域会记录修订，而批评条目只告警。

本包覆盖率按文件 100%，即仓库闸门。`pnpm run verify-translation-pairing` 对 README 对与笔记对均通过。

## 保持原样

[结构化经验提取](2026-09-14-structured-lesson-extraction.zh.md) 拥有"评审器的回答是带下标窗口的决策数组"这一决定；本笔记只为其增加一个动作，不改动它已决定的任何内容。评审器的闸门、冷却、延迟队列、召回与重建路径均未触碰，`rebuild` 依旧是折入已存工件，而不是一条批评路径。`evolution-feedback` 的确定性反思保持原处：它们是 §4.2 为已判定信号写的分析那一半，不用模型撰写，而本批评既不读也不写它们。
