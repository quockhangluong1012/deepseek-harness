# Agent Note: Meta-evolution wiring

Status: implemented

English | [中文](2026-09-22-meta-evolution-wiring.zh.md)

## Problem

`specs/evolutionary-harness-v11-deep-research.md` §26 levels 3–5 and §51 items 29–33 define meta-evolution: the engine learning its own mutation operators, evaluator, budget, and routing instead of always running the same ones. Five packages implemented the mechanism — `evolution-operators`, `evolution-evaluator-strategy`, `evolution-budget`, `evolution-router`, and `evolution-meta` — each with source, tests, and a README, and each module doc named the command verb that reads it (`/operators`, `/evaluator-strategy`, `/budget`, `/router`, `/meta`).

None of the five was mounted in any profile. `ctx.get('evolutionMeta')` and its four siblings were therefore always `undefined`, the optimizer's five recorder seams short-circuited before recording anything, every `recommend()` and `rankOperators()` in the group was dead code, and none of the five promised verbs existed. §54's Phase 10 row read as implemented in the tree while being absent from the shipped product, and the five packages were also missing from the group package table and the generated subsystem page.

## Decision

Make the five stores live, readable, and part of the composed product:

1. **Mount all five in the product profile**, ahead of the `evolution-scorer`/`evolution-optimizer` rows that record into them, with no `config` block — each store's defaults are the intended values.
2. **Register the five read commands** in `dsh-command-evolution`, each reading its own seam through `ctx.get` and reporting `The evolution <name> store is not mounted.` when absent, matching the other optional-seam commands.
3. **Classify the five services and their types** in the two generator gates that own that data: a `SERVICE_PAGE` entry and a type-link exemption per exported type in `scripts/gen-cordis-catalog.ts`, and a service-role row in `scripts/gen-doc-graphs.ts`.
4. **Add the five rows to the group package table** in both languages, and record the bilingual pair.

## Alternatives considered

- **Mount only in the opt-in optimizer overlay** (`apps/cli/config/examples/evolution-optimize/cordis.yml`), where their only writer runs — rejected: nine sibling record-only stores (population, novelty, stagnation, islands, self-model, uncertainty, adversary, lineage, sleeptime) are already mounted in the product profile even though the optimizer is disabled in it. The profile mount is what makes the stores inspectable in the shipped product, and the optimizer's `disabled: true` row is the single switch that decides whether they are populated.
- **Have the optimizer apply the recommendations** instead of only recording them — deferred, not rejected: §26 confines levels 3–5 to after strong governance, and every one of the five READMEs states the store is a record rather than a policy. Applying a recommendation changes what the engine runs, which is a separate decision with its own evidence burden.
- **Fold `/evaluator-strategy` into `/evaluators`** — rejected: the two stores answer different questions (measured verdict health versus learned evaluator trust), and one command's help text could not describe both.
- **Extend the existing commands' usage strings instead of adding commands** — rejected: each store's grammar is multi-verb (`recommend`, `rank`, `spends`, `effectiveness`, …); folding five grammars under four foreign command names would make `/routes` and `/router` indistinguishable to a user.

## Consequences

- The optimizer's five recorder seams now reach a mounted store, so a run records the operator portfolio, evaluator corroboration, budget allocation and settlement, evaluation route, and engine configuration it actually used, and the recommendation each store derives from them becomes readable.
- Each of the five stores is inspectable in the shipped product without enabling anything: the verbs report the empty state that names which run populates them.
- The catalog gates now carry the five packages' vocabulary, so a future type added to any of them fails the generator until it is classified, exactly like the other evolution packages.
- The five bilingual pairing records are no longer truncated, so `verify-translation-pairing` checks them instead of reporting them malformed.

## Deviations from the plan

The plan for this change was generated by a gap audit of the specification's §51 priority map, not by §58 (which was already complete). The audit ranked this block first because four independent auditors reached it separately; the work followed that ranking rather than continuing the §51 item order.

## Fixes found on the way

- `verify-translation-pairing` reported all five packages' `README.i18n.yaml` malformed: the files were committed with only the instruction comment and no hash lines. Their English and Chinese sides are line-for-line and heading-for-heading identical, so the records were written rather than the pairs repaired.
- The `evidence` branch of `/routes` passed `rest[0]` (`string | undefined`) where `EvolutionRole | undefined` was required. The guard now binds the role first, so the argument narrows at the call.
- `gen-cordis-catalog` requires every service-method type to be classified and every catalogued service to name its subsystem page, and `gen-doc-graphs` requires a role row per service. The five packages needed 31 type exemptions, five page entries, and five role rows before either generator would run.

## Testing

`packages/evolution/command-evolution/tests/command-evolution.spec.ts` gains five stub stores and five suites covering, per command: the unmounted error, every usage rejection, the empty state, and the populated rendering including the arithmetic the store itself owns (a batch inside its ceiling and one past it, an under-sampled recommendation, an artifact class with statistics but no ranking, an unusable role argument, a ranking joined to its statistics). The registration test asserts each definition id, name, description, and input hint, and the teardown test asserts each command unregisters. 199 tests pass in the package. `verify-cordis-config` passes 144 config files, and the four generators (`gen-config-catalog`, `gen-cordis-catalog`, `gen-doc-graphs`, `gen-module-graph`) run clean.

## Left alone

The five recommendations are records, not policies: `/meta recommend`, `/operators`, `/evaluator-strategy`, `/budget`, and `/router` report what the stores learned and none of them changes what the engine runs. The stores are populated only while the optional optimizer is enabled. The command-evolution README command table still omits the fifteen reporting commands that landed before this change, so this change added rows for its own five rather than completing the table.
