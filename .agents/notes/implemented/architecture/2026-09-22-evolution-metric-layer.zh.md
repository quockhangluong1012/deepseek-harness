# Agent Note: 演化指标层

Status: implemented

[English](2026-09-22-evolution-metric-layer.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` §55 给出了本框架真正的北极星指标——能力增益除以换来它的算力——并列出了九项支撑指标（学习速度、失败复发、技能增量效用、记忆效用、基准稳健性、回归债、晋级质量、回滚率、评估器可靠性）。此前没有任何代码计算过它们中的任何一项。所有输入其实早已持久化，并且已经建起十一个演化存储专门记录这些输入，但没有任何软件包把其中一个除以另一个，因此这一组只能说清各存储里有什么，永远答不出系统是否在按所花算力变得更优。

有三件事让这一层比一次求和难得多：

1. **一次运行的成本被记录了三遍。** 一次暂存写入把获胜候选的评估记入 `evolution_meta.runs`，把同一次写入的同一三元组记入 `evolution_router.outcomes`，又把该批次评估过的每个变体的累计和记入 `evolution_budget.spends`。其中任意两者相加都会报出实际算力消耗的两到三倍。
2. **指标不存在任何接缝。** `ctx.evolutionMetrics` 是 undefined，所以即便算出了某项指标，也没有命令能报告它。
3. **九项支撑指标中有四项在任何地方都没有输入。** 没有存储把使用技能的运行与不使用技能的运行配对，没有记录统计记忆召回命中或把它与结果关联，没有记录给基准任务打分，也没有任何演化记录含有金额字段。

## 决定

新增一个只读软件包 `packages/evolution/evolution-metrics`（`ctx.evolutionMetrics`）与一个命令动词 `/metrics`。

1. **无域、无状态。** 每个值都在读取时从其它软件包已写入的存储推导，因此本层不可能与其输入脱节，报告永远是那些存储的当前状态。
2. **每项指标只有一个记录来源，且绝不跨范围做算术。** 北极星只读取 `evolution_meta.runs`——唯一同时带有同一次运行的通过与否和成本的记录——并把窗口较新一半的通过率减去较旧一半，再除以整个窗口的 token、算力小时与实际经过的天数。搜索在每个被评估变体上所花的算力改由 `compute-overhead-ratio` 报告，而不是折进一个它并不匹配的分母。
3. **其它软件包已算好的指标直接读取，不重算。** 回归债取 curator 自己的表，回滚率取 canary 自己的状态计数，评估器可靠性取健康摘要自身的比率，失败复发取反馈存储按合并键统计的会话数。
4. **不可测量的指标点名它缺失的记录。** 输入不存在时 `MetricValue.value` 恰为 `null`，并由 `unavailableReason` 点名记录；每个已测量的值都带一个 `caveat` 说明它没有告诉你什么。报告始终携带完整的 §55 指标集，因此一条命令即可回答每一项指标。
5. **在产品配置文件中挂载它，并在两个目录生成器里完成分类**，与其它演化服务一致。

## 考虑过的替代方案

- **新建一个持久化的指标域，把每次报告快照下来。** 否决：所有输入本已持久化，每个值都是它们的纯函数，因此第二份副本只会多一个需要保持同步的东西，而且会重蹈这套存储家族正是要避免的陈旧化失败。这里没有任何东西需要存储尚未保留的历史。
- **把算力分母取自 `evolution_budget.spends`**——唯一统计了每个被评估变体的存储。否决：能力分子是来自另一个存储、针对已暂存运行的通过率，该比率会悄悄混合两种范围与两种覆盖。但保留为一项明确命名的比率，在那里这种不匹配正是所测之物。
- **把一次运行的三份成本记录相加，称之为真实成本。** 否决：它们是一份重复与一份超集，而不是三份贡献；相加会把开销夸大到两至三倍，使北极星的分母失去意义。
- **用可按 token 配价的方式支持美元分母。** 否决：没有任何演化记录带有金额字段，且 `evolution-budget` 与 `evolution-router` 都声明有意不假设任何定价来源。配置出来的价格会让北极星依赖一个本框架从未测量过的数字，因此美元改为报告为不可测量并附上该原因。
- **新增按任务的结果记录，让基准稳健性与技能增量效用变得可测。** 否决，属越界：那是在其它软件包（`evolution-benchmark`、评分器、canary）中改变记录行为；本层的职责是把缺口报告得足够精确，让各存储的负责人自己补上。两个条目都点名了所缺失的确切记录。
- **对不可测量的指标报告为零。** 否决：那会让“没有改善”与“没有测量”无法区分，而这正是北极星所要防止的失效模式。

## 后果

- `/metrics [<taskClass>]` 报告窗口、它所比较的两半通过率、两个北极星分母，以及全部十项支撑指标；每项形如 `- <id>: <value> — <caveat>` 并附来源存储，或 `- <id>: not measured — <reason>`。
- 本层在 `report()` 运行时解析来源，而非挂载时，因此它不施加任何挂载顺序，并把每个未挂载的存储报告为需要它的那些指标的原因。在产品配置文件中所有来源存储都已挂载，因此只要存储有记录就有读数。
- 十二项中有四项在其它软件包记录其输入之前永久不可测量；测试既断言它们报告缺口，也断言缺口点名的是一条缺失的记录而不是某个存储。
- 目录门禁现在承载本层的词汇：六条类型链接豁免、一条服务页面条目、一条服务角色行。签名中新增的导出类型会让 `gen-cordis-catalog` 失败，直到它被分类，与其它演化软件包一致。

## 与计划的偏差

计划来自上一批次差距审计的排序剩余项，其中本块排在首位，因为它是剩余项中唯一测量其它五项、而不是改变引擎行为的一项：§55 自身的准则是，造出一百个技能却只换来百分之一提升的系统，比造出五个换来百分之二十的更差，而此前没有任何命令能回答本系统属于哪一种。其余排序项（只有记录却缺消费者的环路、按任务的结果记录、dreaming 的来源门禁、断言图、检索器接缝）未做改动。

## 顺带修复

- `packages/evolution/evolution-canary/src/index.ts` 在 HEAD 上无法编译：`Object.fromEntries(...)` 产生 `{ [k: string]: number }`，在 `noUncheckedIndexedAccess` 下不可赋值，导致该软件包以及每个引用它的项目 `tsc -b` 失败。改用 `DEPLOYMENT_STATES.indexOf(...)`，省去映射分配且排序结果完全相同。它阻塞了新层自身的构建，因此在此处修复而不是仅作报告。
- 同样的 `Object.fromEntries` 查表写法仍在 `evolution-model-routes` 与 `evolution-router` 中失败，`evolution-optimizer` 则在其能力观测处因 `exactOptionalPropertyTypes` 失败。这三处均已提交且未被本次改动触及；前两处是同一行式的机械修复，优化器那处需要其负责人决定“没有失败”究竟是 `undefined` 还是省略该键。

## 测试

`packages/evolution/evolution-metrics/tests/metrics.spec.ts` 先在不启动上下文的情况下覆盖算术（奇数序列时较新一半多拿一次运行、两处必须拒绝零分母的除法，以及每个算力分母的换算），再启动真实存储覆盖真正要紧的行为：一个六次运行的窗口，较旧一半三次中通过一次、较新一半三次全通过，断言窗口、两个分母与学习速度都等于手算值；每半两次运行的证据下限会扣住增益而窗口仍报告运行数；以及横跨 `evolution-meta` 与 `evolution-budget` 测得的搜索开销比。不可测量的路径在什么都不挂载的情况下启动本层，断言十二个 id 全部在场、每个值均为 null、每个原因均非空，且四项无记录的指标点名的是缺失的记录而不是缺失的存储。支撑指标通过 canary、lineage、curator、评估器健康、遥测与反馈的桩存储读取。本软件包 9 项测试通过。

`verify-cordis-config` 通过 144 个配置文件，`constraints` 通过，四个生成器（`gen-config-catalog`、`gen-cordis-catalog`、`gen-doc-graphs`、`gen-module-graph`）均干净运行且幂等。

## 未做改动

本层只测量，不依测量结果行事。没有加入阈值、告警或自动回滚，也没有任何指标改变优化器所运行的内容。四项不可测量的指标保持不可测量而不做近似：按任务的结果、无技能基线臂、召回命中计数与价格表，都是拥有那些存储的软件包中的记录决策。指标窗口的 `limit` 与支撑指标的全局范围被记为当前约束而非修复项，因为放宽它们需要底层记录并不携带的键。
