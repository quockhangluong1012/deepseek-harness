# Agent Note: 演进式 Harness 的宿主级空闲触发任务注册表

Status: implemented

[English](2026-09-13-evolution-heartbeat.md) | 中文

## 问题

演进式 Harness 在后台自我维护：评审器在每个回合后提取经验，策展器让闲置技能沿生命周期流转，而此后每加一个机制——记忆合并、优化器趟次、索引重建——都会多出一份自治工作。

此前只有策展器持有宿主级调度，而且它是私有的：其间隔、空闲门、定时器与首次运行推迟都绑定在技能生命周期的流转上。因此一个新的自治任务只有两条差路可走——挤进策展器的趟次，让无关工作受制于技能策展的阈值与失败语义；或者自起一个定时器，于是三个维护任务就要背三个定时器、三份空闲观测与三次互不相干的首次运行推迟。

规范的 Heartbeat 机制所指的正是这块空缺：在空闲时间上调度自治维护，并且每个宿主只持有一份。

## 决策

`@deepseek-ai/dsh-evolution-heartbeat` 提供 `ctx.evolutionHeartbeat`，即宿主级的具名维护任务注册表。

消费者调用 `register({ name, intervalHours, minIdleHours?, run })` 并获得一个幂等的注销函数；其任务仅在该注册存活期间运行。插件执行一次被等待的启动时到期检查，随后每隔 `tickMinutes` 在一次 `unref()` 过的定时器上重复，并通过 `ctx.effect` 释放；它观察宿主级 `session/event` 以取得最新活动时刻。完全未观察到活动的宿主按空闲计。

仅当任务的间隔自上次尝试以来已经过去、且已观察到的空闲满足其阈值时，该任务才会被纳入考虑。该阈值默认取引擎的 `minIdleHours`，任务可自行抬高。`runDue` 以时钟、空闲与 `force` 覆盖暴露同一决策；`runTask` 立即运行单个任务；`state` 报告每个任务的节奏与上次结果。

记账为每个任务在存储域 `evolution_heartbeat`（版本 `1`、布局 `per-record`、表 `tasks`）中的一行：上次尝试时刻与最近的失败信息。正是"无此行"这一状态，使新注册的任务被推迟一个间隔，因此挂载引擎不会让所有任务同时开跑。无论成败，每次尝试都会写入该行，因此永久失败的任务按自己的间隔重试，而不是每个 tick 都重试。任务按注册顺序串行运行，拒绝被就地收容——写入 `lastError`、记录一次警告，绝不中断本趟的其余部分。

本引擎未挂载进任何随包发布的 bundle。它尚无已注册的消费者，而一个没有任务的已挂载定时器纯属开销；首个消费者将连同自己的组合行一起落地。

## 考虑的替代方案

**把维护工作并进策展器的趟次。** 策展器已经拥有空闲门、宿主级定时器与首次运行推迟，因此最省事的改法是让其他工作搭它的趟次。它输在耦合上：策展器的间隔、空闲阈值与 stale/archive 阈值描述的是技能生命周期，一个记忆合并任务若继承它们，就会以错误的节奏、因错误的理由运行。其失败语义也是事务形状的——一次流转失败会中止整趟并让记账不盖章——这对彼此独立的维护任务并不合适。

**让每个消费者包各起一个定时器。** 这样每个任务完全自持节奏与故障隔离，也不需要共享注册表。代价是重复：每个包都要重新实现空闲观测、首次运行播种，以及一个 `unref()` 间隔的拆卸；而同时运行数个这类包时，宿主就要背数个定时器，并对"宿主空闲"给出数份互不相干的猜测。

**复用 `@deepseek-ai/dsh-schedule`。** 既有的 Schedule 包已经会持久化工作并按时投递。但它投递的是*进入对话的提醒*，其契约明确写明会话冷掉后不会有任何东西运行——这恰是宿主级维护的反面；复用它要么扭曲该契约，要么让维护只在会话恰好存活时运行。

**用 cron 表达式取代间隔。** 对维护而言，"每日 03:00"这类日历规则读起来更自然，也贴合规范中的 cron 示例。但它会把解析器、时区问题与夏令时语义塞进一个本职只是"没人干活时偶尔跑一下"的插件。间隔加空闲门无需一套调度方言，就能表达真实需求——不要与用户争抢。

## 后果

Harness 从此有了一处统一调度自治工作的地方，新增一个维护机制的成本从"一个定时器"降为"一次 `register` 调用"。引擎自身的表面很小：不注册任何模型可见内容，没有工具，没有 UI，因此既不需要真实组合测试，也不需要快照。

代价是真实且已记录的（见包 README）：任务串行运行且引擎不施加单任务截止时间，因此永不结束的任务会阻塞本趟其余部分，必须自行设界；失败的尝试会写入 `lastRunAt`，因而要等满一个间隔才重试；注册只存在内存中，重启后由挂载的插件重新建立；任务的首次到期检查只做播种，其首次真正运行要等一个间隔。

同一套空闲门现在存在两份实现——本引擎与策展器。把策展器迁移到本注册表之上能让它们合二为一，但那会改变已发布、已测试的策展行为，因此被刻意排除在本次变更之外，且尚无设计负责人。
