# Agent Note: 检索感知的进化

Status: implemented

[English](2026-09-22-retrieval-aware-evolution.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` §39 要求进化不仅能改变智能体如何推理，还能改变它检索到什么，并且以下游任务成功而非检索精度来评判。§23 与 §24 给出了框架：一条被检索到却从未被使用、引用或据以决策的记忆，不能作为检索质量的证据；从结果估计效用，才是相对单看相似度的升级。

仓库此前两半都没有建。没有任何东西在进化检索配置，也没有任何东西把检索改动与它所服务的会话是否成功关联起来：

- 该轴唯一的出现，是 `packages/evolution/evolution-optimizer` 变异算子表面里的字符串 `change-retrieval`；该包以禁用状态发布，而且它命名的是一个维度，并不记录维度。
- `packages/context/active-memory-context` 是检索配置逐回合真正生效的地方——哪条通道运行、图腿扩展多深、命中要越过多少相似度才会被注入——而它对自身运行的配置一无所记。在两个不同配置下被简报过的会话，事后无法区分。
- 做出判断所需的成果证据其实已经存在。`packages/skill/evolution-skill-telemetry` 按技能保存加载过它的会话以及每个会话的已评级结果（`sessionOutcomes`），`packages/evolution/evolution-feedback` 则按失败调用是否可归因到具体工具给每个会话的失败评级。两者都未被任何会变动检索的东西读取。

于是，一个部署可以数月调整召回，却没有留下任何「哪个配置服务了哪些会话」的记录，更不用说哪个配置服务得更好。

## 决策

新增一个包 `packages/evolution/evolution-retrieval`（`ctx.evolutionRetrieval`），按会话记录检索配置，并由下游任务成功推导其有效性。

1. **记录即 §39 的维度词汇。** 一个 `RetrievalConfiguration` 携带检索来源、查询扩展、通道权重、重排器、MMR、记忆作用域、图深度与活动记忆阈值。其规范化键是全部维度按固定数组顺序的取值，因此以不同字段顺序构造同一配置的两个调用方记录的是同一个配置，而该键同时充当归属键的前缀。
2. **一张表，其余全部在读取时推导。** `evolution_retrieval` v1 持有以「配置键 + 会话 id」连接为键的 `attributions`，行为 `{ configKey, configuration, sessionId, at }`。有效性与排名在读取时计算，原因与 `dsh-evolution-budget` 在读取时结算相同：成果证据住在另外两个存储里，并可能在行之下改变——会话在其运行之后才被评级，失败在事后才被归因——而落库的比率会是另一个存储判断的过期副本。
3. **连接本身就是机制，不是新指标。** `gradesOf` 从技能遥测存储的已评级会话结果中取出任务类别与结果，并在反馈存储把某个信号评级为 `complete`（归因到具体工具的失败，而不是仅被观察到的失败）时，把该会话在其加载过的类别上评为失败。两个存储都未评级的会话完全不贡献，遵循 §40 自己的约定：未评级的会话不算证据。若改为在此记录一个指标，就意味着在 curator 的信任遍历旁再放第二个评级者，并与它意见相左。
4. **有效性即成功，排名打分方式与路由一致。** `scoreOf` 是按样本置信度缩放的 beta 先验平滑成功率，因此本存储与 `dsh-evolution-router` 给配置和路由打分的方式完全相同。包内没有任何东西测量相似度或精度：一个提升了召回分数、但其会话失败的配置，排名会低于没有这样做的配置。
5. **推荐按任务类别、以已评级会话数量设门槛。** `minimumSessions` 默认 5，无论分数多高都会拒绝已评级会话更少的配置；README 说明了原因。门槛之下 `recommend` 返回 `undefined`，这是诚实的答案，而不是勉强可用的配置。
6. **产生方就是运行该配置的注入器，且它的写入只是旁路记录。** `dsh-active-memory-context` 在挂载时由已解析配置算出生效中的配置一次，并在会话首个 `agent/pre-step` 为它记录一次，经由用 `ctx.get` 读取的结构化 `RetrievalLedger` 接缝。该写入不被等待，会话在返回前即被标记，回合自身的消息未被触碰——因此挂载与未挂载本存储时简报逐字节相同，存储缺失或失败既不改变搜索，也不改变简报。
7. **不引入 `Retriever` 接口，也不重构检索。** 任务自身的约束引用了 §52：QMD 已被降为 provider 接缝，仓库已有多个检索提供方，而一个把自己插到它们之间的配置记录，会成为在已经可用的提供方之上新增的抽象。

## 考虑过的替代方案

- **记录检索精度并以它排名。** 否决：§39 与 §23 存在，正是因为精度是会误导的代理——相似度更低但决策效用更高的记忆应当胜出。以该机制本来要绕开的那个量排名，会让这个包失去意义。
- **由本包给会话评级，并把结果存进归属行。** 否决：两个已发布的存储已经在给会话评级，这里的第三个评级者要么重复 curator 的信任遍历，要么为「这个会话做得不错」发明第四套惯例。归属行记录跑了什么；评级留在它被测量的地方。
- **只记录注入器实际设定的项（通道、深度、阈值）。** 否决：记录是规范的维度词汇，而为此挂载无法变动的维度（`weights`、`reranker`、`mmr`、`queryExpansion`）记录已发布的选择，正是为了让优化器把自己变动了这些维度的配置记入同一张表，并与注入器的配置平等比较。
- **对遥测包与反馈包建立硬依赖。** 否决：`packages/context/active-memory-context` 的图腿已经通过结构化接缝读取一个可选服务，这里沿用同样的纪律，使缺少其中一个存储的部署改由另一个推导有效性，而不是加载失败。
- **以分数而非数量作为推荐门槛。** 否决：置信因子只缩放分数，因此一个有四个已评级会话的配置可以高过一个测量充分的落败者，而它仍然是 README 所说的「某天下午的一批证据」。门槛是数量；分数只用于排列越过门槛者。
- **逐回合记录而不是按会话记录。** 否决：两个证据存储评级的粒度都是会话结果，逐回合归属需要没有任何存储记录的逐回合结果，还会让同一个评级本就能回答的行数成倍增长。
- **让注入器导入本包的配置类型。** 否决：哪怕只是类型导入，也会为一个结构上很简单的形状带来工作区依赖与 tsconfig 引用，而注入器自己的文件已经以结构化方式声明它的可选接缝。两侧由 §39 词汇对齐，投影只是一个导出的纯函数。

## 后果

- 新增域 `evolution_retrieval` 版本 1，含一张 `attributions` 表。非法行会让域打开时响亮失败，因为推荐信任它读到的数字。
- `dsh-active-memory-context` 每个会话多出一次可选写入，行为上别无变化：不调用模型、不改变提示词、回合路径上不同步等待存储，而存储拒绝写入时只记一行 debug 日志。
- 某个配置达成了什么，可通过 `ctx.evolutionRetrieval.effectiveness(taskClass)` 与 `recommend(taskClass)` 看到。推荐在某个挂载把它当作策略之前都只是记录：`dsh-active-memory-context` 会在自身默认关闭的 `taskAwarePolicy` 字段之后按轮次的任务类别采纳它（见[任务感知检索策略](2026-09-22-task-aware-retrieval-policy.zh.md)），而没有任何东西会自行重新配置注入器，这与产品配置中每一行进化插件所持的姿态一致。
- 此处没有任何内容抵达模型提示词、工具 schema 或会话事件，因此本包不发布不变的伴生检查——归属表是此状态的唯一副本，没有第二个独立观测可供比对。
- 产生方的接缝是单向的，且两个方向都可选：未挂载本存储的部署不记录任何东西，挂载了本存储却没有证据存储的部署会记录下推导不出有效性的归属。

## 与计划的偏离

计划要求该存储在产品中被填充。挂载行本身位于 `packages/bundle/web-app/cordis.patch.yml`，包注册位于生成的工作区文件（`tsconfig.base.json` 别名、`tsconfig.host.json`、bundle 清单），这些都不属于本任务所有。产生方已经完成并在其接缝后启用；行、注册与 `pnpm install` 链接由集成者负责。

## 途中发现的修复

无。两处疑虑经过调查后被排除。第一：注入器是否会为记录类型需要对本包的真实工作区依赖——结构化接缝使其不再必要。第二：`verify-package-readme-model-experience` 门禁是否会接受新包的短式「模型体验」小节而无需白名单条目——它不会；审计还发现 19 个已提交的进化与技能 README 处于同样状态，因此缺失的同族条目是上报给集成者，而不是在 `scripts/` 里绕过。

## 测试

`packages/evolution/evolution-retrieval/tests/retrieval.spec.ts` 在没有上下文的情况下覆盖纯函数那一半：配置键在字段顺序变化下稳定，并能区分全部十一种单维度变体；评级连接在已评级结果与反馈失败之间取前者、在反馈失败与无之间取失败；同一会话每个类别只计一次；有效性折叠保留滚动比率与最新时刻；同一会话会按其服务过的每个配置各记一次，而未评级的会话被丢弃；排名按分数排序并以键为平局判据，且只在门槛之上给出推荐。

`packages/evolution/evolution-retrieval/tests/store.spec.ts` 在内存后端上启动真实域，钉住真正重要的行为：同一会话第二次记录只保留一行与其首次时刻，样本数不翻倍；有效性来自打桩的遥测结果与被反馈归因的失败，两个存储都未挂载时为空；同一任务类别上的两个配置推荐出会话成功的那个，较弱者不会被提供；低于门槛的配置即使分数更高也不给出推荐；归属在通过 zod 规范重启后仍然存在；存储启动前读取抛出异常。

`packages/context/active-memory-context/tests/index.spec.ts` 新增三个用例：注入器恰好记录生效中的配置（`graph-first` 升级记作 `source: 'graph'`，连同配置的深度与阈值），且注入的简报与未挂载该存储的同一场景逐字节相同；同一会话的第二步不再记录；拒绝写入的存储仍让回合得到简报，并留下 debug 日志。

两个包都满足逐文件 100% 覆盖率门槛（retrieval：85 条语句、43 个分支；active-memory-context：180 条语句、86 个分支）。

## 未触碰的部分

`packages/evolution/evolution-optimizer` 变异表面中的 `change-retrieval` 字符串保持原样：该算子命名的是一个优化器会变动的轴，而本包记录配置，并不声称生成配置。没有任何东西会自行消费推荐：注入器严格按配置运行，直到某个挂载开启 `taskAwarePolicy`，后者通过一条纯决策规则按轮施加推荐的通道、范围、图深度与阈值（见[任务感知检索策略](2026-09-22-task-aware-retrieval-policy.zh.md)）。

在两个配置下运行过的会话会把结果同时计入两者。把一次结果分摊到服务过它的多个配置，需要两个证据存储都未记录的逐回合归属；README 陈述了这一限制，而不是近似它。

存储是宿主全局的，不按作用域键控：归属是全局行，按工作区视角需要给域加作用域键，这与 `evolution-evaluator-health` 和 `evolution-router` 为自身表所记录的限制相同。
