# Agent Note: 演化驱动

Status: implemented

[English](2026-09-22-evolution-actuator.md) | 中文

## 问题

`specs/evolutionary-harness-v11-deep-research.md` 描述的是回路，而仓库此前只建成了它们的记录一半。§7 要求岛屿之间"按代际/预算计划"迁移；§18 的发布以 `MONITOR → rollback / learn` 收尾；§32 说停滞的技能"自动切换策略"；§43 把不确定的评估变成"用于额外评估的高价值任务"。这些机制每一个都以持久存储的形式存在，却没有任何东西对它们采取行动：

- `evolution-canary` 持有一部五态阶梯，只执行调用者点名的流转。它自己的 README 就点出了缺口：该存储"记录的是获胜者的实测三元组，而不是相对生产基线的隐藏响应比较；那种基于重放的比较是暂缓的监视工作（§18 的比较步骤）"。
- `evolution-islands` 在每条排程行上计算 `due` 标记，而 `migrate` 的唯一调用者是人工命令 `/islands`。`MigrationReason` 的 `diversity` 取值根本没有写入者。
- `evolution-stagnation` 从 §32 阶梯推导出 `strategy`，并把字符串交给 `/stagnation` 渲染；没有任何代码执行该档位。
- `evolution-uncertainty` 推导出按优先级排序的评估队列，而 `resolve()` 没有任何生产调用者。
- `evolution-curriculum` 暂存有据可依的任务，而进入基准存储的唯一路径是人工命令 `/benchmark admit`。

产品配置文件把这一姿态明说了：每一行演化配置"是记录而非策略：此处没有任何东西改变引擎运行什么"（`packages/bundle/web-app/cordis.patch.yml`）。这说法是准确的，也意味着引擎可以无限期积累证据而从不据此行动。

## 决定

新增一个软件包 `packages/evolution/evolution-actuator`，它注册五个心跳任务——每个已记录裁定一个——并为每个任务配一条纯决策规则。

1. **驱动是一个包，而不是五个。** 五个回路共用一份契约：读取已记录的裁定，经由已经接受它的存储执行该裁定所许可的步骤。宿主会一并启用它们，而五个包意味着在一个已经承载三十行演化配置的 profile 中再加五行。本组现在有一个负责写的包（`evolution-optimizer`）、一个负责读的包（`evolution-metrics`），以及这个负责行动的包。
2. **触发器是心跳，依赖是声明式的。** `inject = ['evolutionHeartbeat']` 让挂载顺序无关紧要：调度器存在时插件才应用，而不是在 apply 时读取一次 `ctx.get('evolutionHeartbeat')`。存储保持为可选缝，因此未挂载的存储只让那一个回路成为空操作，其余四个照常工作。
3. **每条决策规则都是纯模块**——`rolloutDecision`、`migrationTarget`、`recoveryStep`、`benchmarkInput`——因此规则变更是一次单元测试，而不是一份宿主夹具，回路只执行规则所指名的调用。
4. **每个回路在构造上都是幂等的**，这正是节奏安全的原因：已决的发布会离开 `canary`，已记录的迁移会重置其泳道的到期标记，课程存储跳过已开放的任务，基准存储按内容去重，不确定性排空丢弃它所操作的信号。
5. **发布只会被结束，从不会被开启。** `shadow → canary` 是 §49 交给运维者的中风险步骤，因此监视器只决定已经在线的发布：它提升记录证据相对在任者站得住的补丁，回滚语料未通过、或按引擎自身精英序更贵的补丁。
6. **没有可写目标的档位只报告，不发明。** §32 的阶梯从多样性爬升，经新变异算子、新任务、新评估器，直到切换模型。其中两个档位点名的东西有存储接受——迁移到该技能新颖泳道的 `diversity` 迁移，以及由其实测缺口导出的课程提案。其余是评估器策略与模型路由这两个包自己的决策，且没有任何存储记录这种切换，因此 `recoveryStep` 对它们返回 `unactionable`；`newOperators` 后来作为对 `evolution-operators` 推荐的一读而变得可行动（见 `2026-09-22-adversarial-probes-and-budget-gates.md`）。
7. **在产品配置文件中挂载它**，放在最后，即在它所读取的每个存储之后。

## 考虑过的替代方案

- **五个包，每个回路一个。** 否决：这些回路共用一份契约与一个触发器，想要其中一个的宿主也想要其余；按回路的 `Config.loops` 字段给出了同样的可选择性，却不必付出五行 profile、五对 README 与五个目录条目。
- **在每个存储内部扩展出各自的消费者。** 对其中三个回路否决：停滞恢复横跨停滞、岛屿、种群与课程四个存储，排空横跨不确定性与基准，准入横跨课程与基准。把它们塞进存储会让每个存储依赖其兄弟，而这正是可选缝模式要避免的耦合。
- **由命令平面而非心跳来驱动。** 否决：`/canary`、`/islands` 与 `/benchmark admit` 已经按人的指令行动。缺口在于没人发问时无人行动，而命令按定义就是有人在发问。
- **提升三元组未测量的发布。** 否决：`rolloutDecision` 返回 `hold`。从未被测量的补丁没有证据，而存储的 `triple: null` 正是为了说明这一点。
- **仅按 token 决定发布。** 否决：该判断遵循引擎的精英序——先 pass，再计费 token，最后在 token 相同时比墙钟时间——这与 `evolution-stagnation` 的 `betterThan` 所用优先级相同，因此发布与停滞运行以同一方式评判补丁。
- **由不确定性信号合成基准任务文本。** 否决：没有任何存储为信号保存生成的任务，在驱动层里发明提示词文本会让基准存储的内容无法追溯。被准入的任务携带所观察到的注记，README 把这一点列为限制。
- **课程提案被准入后即退役。** 否决：`/benchmark admit` 让它保持开放，依赖基准存储的内容哈希；两条路径对同一提案的生命周期意见不一，比一条重复去重写入的路径更糟。
- **在每条节奏旁再加一个按回路的开关。** 否决为八个字段做一件事：`loops` 负责选择，其余每个字段都保持为一条节奏或一个阈值。

## 后果

- `ctx.evolutionHeartbeat.state()` 中会出现五个心跳任务：`evolution-rollout-monitor`、`evolution-island-migration`、`evolution-stagnation-recovery`、`evolution-uncertainty-drain`、`evolution-curriculum-admission`。每个都只在间隔已过且宿主保持空闲之后运行，因此挂载本包不会立刻改变任何东西。
- 这些回路做了什么，在它们写入的存储中可见——`deployments`、`migrations`、`proposals`、`tasks`——经由已经渲染这些存储的命令；每个任务的结果则在心跳的 `lastError` 中。
- 拒绝某个动作的存储（例如有人先推进了同一次发布）会让该任务的那次尝试失败，心跳将其记录并按间隔重试，而不停止其它任务。
- 本包不开启任何域，因此不发布不变式伴随包；它所操作的每个值都属于记录它的那个存储。
- 目录门禁因此多出一行软件包、一张配置表与一个模块图节点。

## 与计划的偏差

计划是上一批缺口审计中排好序的剩余项，其中把"只记录"的回路排在最前。有两项被有意排除在本批之外：按任务的结果记录，与 dreaming 的归属门。前者是 `evolution-benchmark` 与 scorer 中的记录变更，而非驱动；后者是 `evolution-dreaming` 提升路径内部的门，而不是对已记录裁定的回路，并已随该包落地（见[归属、合并与回滚的决定](2026-09-22-dreaming-attribution-merge-and-rollback.zh.md)）。结果记录与检索接缝仍然开放。

## 途中发现的修复

无。有一处怀疑经过了排查并被排除：产品配置文件中有十五行演化配置点名了一个 `Config` schema 只含带默认值字段、而该行本身不带 `config:` 键的插件，且对这类 schema 用无参数的 `ctx.plugin(plugin)` 会被拒绝。加载器并不传 undefined——把 `@deepseek-ai/dsh-evolution-skill-telemetry`（严格的 schemastery schema、YAML 中无 `config:` 键）经由 app-boot 的 `boot()` 路径启动，会到达等待注入状态而不是配置错误，因此那些行按原样就是正确的，新增的行同样不需要 `config:` 键。

## 测试

`packages/evolution/evolution-actuator/tests/actuator.spec.ts` 先在无上下文的情况下覆盖每条决策规则（发布判定表，含未测量的 hold 与两个成本回归分支；泳道轮转及其回绕与单泳道拒绝；档位映射，含那些不可执行的策略（`newOperators` 后来变为可行动，见 `2026-09-22-adversarial-probes-and-budget-gates.md`）；以及队列到基准的映射及其空输入拒绝），随后启动心跳、基于内存后端的七个真实存储与插件本身，覆盖真正要紧的行为：

- 同一轮中通过的发布被提升、失败的发布被回滚，而随后通过但比已提升在任者更贵的补丁在下一轮回滚；
- 每条到期泳道都迁移该技能的精英，而同一瞬间不会重复迁移；
- 处于 diversity 档位的停滞技能把精英移入新颖泳道，处于 newTasks 档位的技能暂存由其打桩的遥测与追踪缺口导出的任务，两轮之间只暂存一次；
- 不确定性排空用信号注记准入队列中的任务，并清空队列；
- 课程准入准入一份开放提案，并在第二轮不再准入任何东西；
- 每个回路在自身存储都未挂载时仍记录一次成功的轮次。

`verify-cordis-config` 通过 144 个配置文件，`constraints` 通过，四个生成器运行干净且幂等。

## 未触碰之处

驱动只作用于已记录状态，且不门控任何东西：被提升的发布不会让技能可见，被准入的基准任务不会运行，任何回路都不触及模型提示词。因此 §58.12 的"只记录、不强制"边界在本次变更后依然成立。不可执行的阶梯档位保持不可执行，而不是用一个配置好的评估器或模型开关去近似，因为那些策略属于拥有评估器集合与路由表的包；`newOperators` 后来作为对 `evolution-operators` 推荐的一读而变得可行动（`2026-09-22-adversarial-probes-and-budget-gates.md`）。各回路是全宿主范围而非按作用域，并且在心跳的一轮内顺序执行；两者都作为当前约束记录在案而非被修复，因为按作用域的策略需要在底层域上添加作用域键。
