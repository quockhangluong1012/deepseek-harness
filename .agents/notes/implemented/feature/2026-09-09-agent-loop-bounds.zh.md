# Agent Note: Agent-loop 步骤与重试上限

Status: implemented

[English](2026-09-09-agent-loop-bounds.md) | 中文

## 问题

持续失败的步骤会持续消耗模型调用：任何无条件返回 `{ kind: 'retry' }` 的 `agent/request-error` 监听器都会无界地重跑失败步骤，`always` 模式的提供方策略自身也永不耗尽。工具调用轮次具有相同的形态：每个暂存了更多工作的工具结果都会延续当前轮次。两种循环都会无节制地消耗时间、token 与费用，且部署方无法通过配置设定上限。

## 决策

循环强制执行两个上限，两者都是校验过的 `Config` 字段，也是 `agent-loop` 分节下的实时用户设置。

`maxSteps`（默认 `100`）将继续进入更多步骤的轮次以 `max-steps` 结束。上限仅在超出预算时触发，因此恰好在上限处正常结束的轮次仍按正常结束；与 `max-tokens` 一样，首次命中上限的结果拥有轮次结局，后续步骤永不降级，即使 steering 排入了更多工作，轮次也会停止。

`maxRequestRetries`（默认 `10`）限制每个步骤接受的 `agent/request-error` 恢复次数。超出上限的恢复保持终态，并携带 agent、轮次、步骤与次数告警；`0` 表示完全禁用请求恢复。提供方重试策略在上限之下保持权威：其默认允许 5 次恢复，为循环上限的一半，因此普通的 `normal` 模式恢复永远触及不到它。取消仍然优先于重试决定。

## 上限语义

两个上限都在每次决策时穿透读取实时配置，因此已提交的设置变更会约束下一步骤或下一次重试，而不干扰正在进行的那一个；被拒绝的写入让运行中的循环保持在上一次有效的上限上。重试计数器随每个步骤重置，步骤上限与之组合：无论每个步骤的恢复如何，一个轮次至多受 `maxSteps` 个步骤约束。两个上限都不限制 token、时间或费用；需要限制这些的策略仍从既有生命周期扩展点（如 `agent/turn-stopping`）执行取消。

## 曾考虑的替代方案

**仅依赖 `dsh-llm-retry`。** 它只按提供方与策略键约束 `normal` 模式策略；`always` 模式与自定义恢复监听器绕过它，而这正是循环上限要阻止的风暴。

**在会话日志中持久计数重试。** 上限是本地部署选择，不是模型可见状态；持久计数会在不改变模型所见内容的前提下增加会话格式负担，因此计数器保留在步骤的进程本地。

**在循环中设置总括式工具超时或 token 预算。** 已拒绝：循环中的取消是协作式的，硬终止需要 worker 或进程边界；逐调用限制属于声明它的 guard 策略，token 或时间预算属于挂载在 `agent/turn-stopping` 上的策略插件。

**更低的默认值。** 当步骤中途切换路由、每个策略分别计数时，提供方策略栈在一个步骤内合法消耗超过 5 次恢复是可能的，因此循环默认值保持为提供方默认值的两倍，而不与之取齐。

## 后果

每个轮次最坏情况下的模型调用数受 `maxSteps` 个步骤乘以每步 `1 + maxRequestRetries` 次恢复约束。默认路径的 transcript 不变：提供方策略先于循环上限耗尽，因此录制会话快照无需刷新。单步内确实需要超过 10 次恢复的部署必须显式调高上限；超出上限的失败以终态提供方错误呈现，告警是上限触发过的唯一记录。

## 测试

`request-error.spec.ts` 针对始终重试的监听器锁定默认上限、更小的配置上限、零值禁用，以及加载时对负数与小数的拒绝。`settings.spec.ts` 锁定设置的叠加与写入时拒绝。`request-reconstruction.spec.ts` 锁定纯工具变更只记录 header `change` 而不带 series 标记，共享的 series 谓词保持该行为。逐文件 100% 覆盖率门禁让每个上限分支都得到执行。
