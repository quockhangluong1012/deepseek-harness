# Agent Note：无循环改动的 LLM 路由回退

Status: implemented

[English](2026-09-11-llm-fallback.md) | 中文

## 问题

死掉的提供方会终结回合：`llm-retry` 拒绝一次失败后，循环重发同一路由或放弃，于是配置了健康路由的 agent 被一次故障拦停。规范以路由回退加按路由断路器与密钥轮换钩子作答——但循环在 `{ kind: 'retry' }` 后重发完全相同的请求对象，乍看回退改路由必须动循环。

## 决策

在 `llm/` 分组交付 `@deepseek-ai/dsh-llm-fallback`，不动循环。循环每次尝试重发 `agent/request` 瀑布，其契约就是"返回替换即切换"（现成的 `model-selection` 先例），因此本包把永远先委托下游的外层 `agent/request-error` 包装器，与为失败步骤下次尝试服务的 `agent/request` 覆盖配对。被拒绝的失败记到其路由名下，跳过断开的断路器与刚失败的提供方，按配置顺序挑选；轮换钩子在切换前运行；持久化 `llm/fallback` 事件先于 `{ kind: 'retry' }` 回答追加。下游重试永远保留，不被取代；切换时剥离继承的 reasoning effort，因为不同适配器可能拒绝上一路由的 effort 旋钮。断路器状态是进程本地，暂无成功重置；密钥轮换以可选 `ctx.llmFallbackKeyRotation` 到达，而不是 Config，使生成的配置目录保持纯数据。

## 备选方案

- **给 `RequestErrorAction` 加路由载荷。** 否决：那需要改循环（架构地图更新、SDK 投影、快照），而现有 `agent/request` 契约已能产生同样行为。暂存加替换以零成本实现同样的可观测切换。
- **内层姿态（注册在 `llm-retry` 之后）。** 否决：处理的重试短路而不委托，内层回退既看不到已处理的失败，也永不能取代。外层包装器看到一切失败且照样保留下游重试；行顺序由测试锁定。
- **把重试后恢复的抖动计入断路器。** 否决：只有下游拒绝的失败才进入求值，因此断路器计数的是放弃而不是瞬断。成功重置需要 `assistant/message` 观察者，另行到来。
- **轮换钩子后再加一次中止检查。** 否决：循环的水瀑后 `throwIfAborted` 照样获胜，垂死回合至多落一个杂散事件——而该检查不扭曲钩子签名就不可测。
- **掩盖下游监听器抛错。** 否决：抛错的恢复链就是 bug，切换会藏起它。抛错向上传播；只有轮换钩子的抛错被收容（警告并继续）。

## 后果

提供方故障如今带着每次切换的可审计事件跨已配置路由迁移会话：状态界面可以像跟随 `llm/retry` 一样跟随 `llm/fallback`。切换后的路由经由循环的持久化请求头跨回合保持，不自动返回；常开重试策略永不拒绝从而饿死回退；每次切换消耗一次共享 `maxRequestRetries` 步骤。已发布的 web-app bundle 把该行挂载在 base 层 `llm-retry` 行之后，且轮换列表为空，因此在部署方指定路由并通过上下文钩子轮换密钥之前，回退保持关闭；无论行序如何，外层包装器的姿态都成立。

## 测试

十三个用例锁定：配置默认值与路由复制、大声拒绝、端到端提供方切换与日志事件、挂载 `llm-retry` 时的下游重试保留、不合格码与无路由的终结拒绝、跨三回合的断路器断开/跳过/冷却与链式回退标识、密钥轮换调用与抛错存活、回合取消纯洁性、销毁后静默加过期回调拒绝。按文件 100% 在语句、分支、函数与行上成立。
