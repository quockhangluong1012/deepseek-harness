# Agent Note: 评审器延迟队列

Status: implemented

[English](2026-09-12-evolution-reviewer-defer-queue.md) | 中文

## Problem

评审器在 `turn/end` 提取经验。当提取不与任何东西竞争时，这是正确的时机；当提取与实时会话争夺同一个 provider 时，则是错误的时机：每个受门控的回合都要先付一次额外生成，用户的下一条消息才能得到服务；而一连串短回合会为彼此高度重叠的快照每个回合都付一次。

`specs/evolutionary-harness.spec.md` 把缺失的契约记为评审器自有的延迟：`defer: auto|never` 加 `deferMaxAgeMs`，在回合结束时入队、按会话合并、超过年龄上限强制执行、只在内存中。它与 `deferContext` 不同，后者延迟的是上下文物化而非评审。

## Decision

`defer` 默认为 `auto`：受门控的回合进入按会话的内存队列，而不是立即提取。`deferMaxAgeMs` 默认为 `1800000`，限制排队回合的年龄，从该会话的**第一份**快照起算，因此持续产生回合的会话仍会在上限内完成一次提取，而不会无限推迟。后续回合替换已排队快照的 `turn`/`rows`/`route`，而最初的截止时间与计时器保持不变：合并让一个安静窗口只有一次提取，而不是每回合一次。

刷出会把到期条目送进即时路径所用的同一条按作用域 promise 链，因此同一作用域永不并发两次提取，被取代的条目也照旧被丢弃。`defer: never` 恢复回合结束时的提取。`/refine`（评审器的 `rebuild`）从不查询该队列。

会话释放与 teardown 会丢弃排队条目并清除其计时器而不提取：它们中止受限的后台工作，而在会话正在拆除时启动一次新的模型调用恰恰相反。门控顺序不变——归属、产出索引、`enabled`、`minTurnTextBytes`、冷却、路由——且冷却刻意不在刷出时复查，因为排队回合已经通过过它。

队列不附带任何工具白名单。规范中的 `extraTools[]` 属于尚未落地的 subagent 分支；进程内的提取是一次无工具的请求，白名单字段不会有读者。

## Consequences

稳态下每回合的模型调用降到零；会话结束后的经验最晚在 `deferMaxAgeMs` 之内落盘。代价是记忆最多陈旧该上限的时间，这正是规范选择的取舍：在此期间简报继续沿用上一份文档。

排队快照只在内存中。在截止之前发生重启、teardown 或 `session/disposed` 会丢失该回合的提取——记录保留上一次提取写入的内容，下一回合从被观测到的后缀重建，而不是重放丢失的那一份。

`timer.unref?.()` 让队列不会把事件循环钉住，因此没有其他工作可做的进程仍可在一个回合排队等待时退出。

## Verification

`tests/reviewer.spec.ts` 固定可观察行为：`defer: never` 照旧在回合结束时提取；`defer: auto` 配 `deferMaxAgeMs: 0` 同步不做任何提取，并在计时器回合后恰好提取一次；默认值（完全没有 `defer` 键）进入排队；刷出前关闭的两个回合只产生一次提取，且其笔录是较新回合而非较旧回合；teardown 丢弃已武装的条目而不提取；会话在计时器触发前被释放时，该计时器不启动任何工作。`tests/config.spec.ts` 固定 schema：未知模式与负上限抛错，`Config({})` 解析为 `auto`/`1800000`。按文件 100% 在语句、分支、函数与行上成立。

## Alternatives considered

**运行时可用性信号。** 像上游设计那样等待「本地模型忙」标志。否决：本仓不存在这种信号，凭空发明会把评审器耦合到某个 provider 细节上；年龄上限在没有它的情况下给出了有界延迟。

**以最新回合为基准做固定延迟。** 否决：繁忙会话会把自己的提取无限往后推；以第一份快照为基准把无界等待变成了上限。

**持久化排队快照。** 目前否决：队列是调度细节，而持久队列需要自己的格式、迁移叙事与去重规则，只为以分钟计的窗口服务。

**让提取与回合同步。** 否决：那会把后台评审变成它本就设计为置身其后的用户可见延迟的一部分。
