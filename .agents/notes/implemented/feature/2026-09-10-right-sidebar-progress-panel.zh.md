# Agent Note: Right-Sidebar progress panel

Status: implemented

[English](2026-09-10-right-sidebar-progress-panel.md) | 中文

## Problem

一个会话的工作状态散落在各自回答更窄问题的界面上。清单在一条默认收起的输入区停靠条里，读者不展开就只能看到计数标题；产出文件出现在每个写过文件的轮次收尾消息之下。于是"这个会话在做什么、已经产出了什么"需要不断滚动才能看清，而专为这类会话级视图而建的右列——右侧 Sidebar——默认收起并停在引导页，根本没有进度界面。

## Decision

新的浏览器插件包 `@deepseek-ai/dsh-client-ui-progress` 贡献一个右侧 Sidebar tab 类型（`kind: progress`，id `@deepseek-ai/dsh-client-ui-progress`），web-app 装配把它与 `ui-sidebar-files` 并列加载。

- **它不发布任何新事实。** 正文只读另外两个包已经发布的事实：Host 计算的 `todos` 投影提供清单，`ui-deliverables` 为每个写过文件的轮次发布的 `deliverables` 轮次数据提供产出文件。没有新的会话事件、没有新的投影单元、没有新的 Remote 命名空间、没有 store，也没有注入面——组件所需的一切都经框架的会话 hook 到达。
- **它画两个分区。** 先是任务（每行以自身状态作为无障碍名称；已完成是勾，待处理是虚线圆环，进行中是同一个圆环在转动；标题行按已完成数对总数计数），然后是产出文件：按首次出现顺序、每个路径只列一次的产出路径，每行显示路径最后一段，并经该 tab 自己的 `openResource` 打开文件，地址由 `fileAddressFor` 生成。
- **它只在代理工作时自行打开，且每个会话只开一次。** `auto-open.ts` 监听 `ctx.sessions.list` 的当前选择，并跟随该会话的绑定——它自身的生命周期快照、`todos` 投影面与 Chat target。若某会话显示期间它的代理运行过，该会话的首个进度就会打开并展开面板；运行被锁存，因此快速轮次即使在其文件到达客户端前就已结束，仍然会打开。选择移开时释放跟随，打开后立即停止跟随，因此之后到达的进度不会重新打开读者再次收起的面板。唯一的记忆是"已打开会话"集合。
- **它占用既有坑位。** 不新增 `SlotMap` 键：正文注册进以类型 id 为键的 `sidebar.right.pane.tab` 坑位，引导页入口（order 30）为该类型给出与随包类型并列的手动打开入口。

## Alternatives considered

- **在新包里复制写操作词汇。** 否决：`write`/`edit`/执行写操作的 `str_replace_editor` 参数解析及其结果关联已存在于 `ui-deliverables`，第二份定义会漂移。导出纪律禁止一个功能插件导入另一个功能插件的运行时值，因此面板读取该插件发布的轮次数据——即对 `ConversationTurnDataMap` 的类型合并。
- **新增 Host 侧产出文件投影。** 否决：该词汇按设计属于客户端且按轮次成立（Web 层从原始调用/结果事件推导，从不读收尾正文）；Host 单元会重复这份解析，还要加 wire 键、schema 和版本，换来的只是本面板用手中的窗口就能算出的汇总。
- **发送即打开。** 否决：右列占据视口很大一部分，在会话还没有任何内容可报告时打开，会让每个新对话都先看到一个空面板。
- **只看进度、不看运行。** 否决：打开一个会话会加载它历史中的一切，因此该列会在每次重新加载、每次回到旧会话时自行打开——而右侧 Sidebar 已记录的默认就是"重新加载后每个会话都是收起的"。以"会话显示期间运行过"为条件，无需任何持久化标志即可区分正在进行的工作与已加载的记录。
- **在既有坑位里放一个始终挂载、渲染 null 的哨兵组件来触发打开。** 否决：那会为了让一个副作用跑起来而占用语义完全不同的坑位（头部操作、输入区停靠位）；同样的事实可以从 apply 世界经拥有它们的服务直接读到。
- **把 `progress` 作为每个格的默认 tab，替代引导页。** 否决：为了一个面板而改变每个会话、每个其他 tab 类型的默认界面。
- **由 tab 正文自己触发打开。** 直接否决：tab 正文只在它的 tab 打开时存在，因此它不可能成为打开该 tab 的原因。

## Consequences

面板不新增模型可见输入：没有提示词分区、没有工具 schema、没有会话事件，因此既无 token 与 KV 缓存影响，也不改变任何持久化或 wire 格式。它的代价是装配里多一插件行和一个引导页入口。

两个限制来自事实的来源。产出文件列表覆盖 Chat target 已加载的轮次，更早的历史要等加载后才出现；跟随 Chat target 会为该会话激活它，这意味着读者访问过的会话即使正在看别的视图，Chat target 也会建起来（这是 target 的第二个消费者被记录的用法）。两者都写进了包的 README。

自动打开的记忆属于插件自身：重新加载后每个会话都收起，清单始终为空、轮次也没有产出的会话永不打开面板，读者再次收起的会话也保持收起。

## Testing

客户端规格钉住两处推导（按轮次顺序汇集、按首次出现去重、缺失的轮次数据与缺失的行）、打开策略（每个会话一次、运行按会话锁存、选择切换时释放、绑定尚未就绪时重试、无选择时不动作、dispose 时释放）、对真实 tab 注册表的注册与打开接线，以及面板的渲染、计数、文件地址与打开调用。

`apps/web/tests/progress-panel.e2e.ts` 在真实 Chromium 中驱动录制的 workspace-write 对话，端到端断言随包行为：对话进行期间该列是收起的，写操作自行打开它并停在 Progress tab，行内带有产出路径，点击后落在 Sidebar 的文本预览并显示文件内容。该列自身的验收 `apps/web/tests/sidebar-right.e2e.ts` 保持不变并全部通过，这正是"已加载的历史与进程内植入的会话事件不会打开该列"的检查。
